<objective>
Ship the admin half of RBAC-03 and all of RBAC-04's write path: a scoped review queue, an
approve/reject endpoint, and a suspend/reinstate/revoke endpoint — each one authorized by the
single helper from plan 05-02, each one requiring a reason, and each one writing an append-only
audit row.

Purpose: this is where ROADMAP criteria 2, 3 and 5 become real. It is also where the
load-bearing property of the phase is implemented: approval creates a grant row, and that grant
still passes through the full requirement list on every subsequent authorization check — so
Phase 6 can block it by adding one requirement, without touching anything built here.

Output: one use-case module, three API routes, one test file.

**2. `reviewApplication(deps, actorUserId, applicationId, input: ReviewApplicationRequest): ResultAsync<ReviewApplicationResponse, AppError>`**
where `deps = { now?: () => Date }`. Order matters — do not reorder:

1. `findApplicationById(applicationId)`; null → `errAsync(notFound('Application'))`.
2. If `application.status !== 'submitted'` → `errAsync(conflict('Application already decided'))`.
3. `requireReviewAuthority(actorUserId, { spaceId: application.space_id, targetRole: null,
   action: input.decision === 'approve' ? 'approve' : 'reject' })`.
   **The authorization call must come after the application is loaded (its space is needed) and
   before any write.**
4. `decideApplication(applicationId, input.decision === 'approve' ? 'approved' : 'rejected',
   actorUserId, input.reason)`. A `null` result means another reviewer won the race →
   `errAsync(conflict('Application already decided'))`.
5. Audit the decision:
   `insertAuditEvent({ subject_type: 'community_manager_application', subject_id: applicationId,
     event: input.decision === 'approve' ? 'approved' : 'rejected',
     subject_user_id: decided.user_id, actor_user_id: actorUserId,
     role: 'community_manager', space_id: decided.space_id, reason: input.reason, detail: null })`.
6. On **reject**: return `{ application: toManagerApplication(decided), grant: null }`.
   On **approve**: `insertGrant({ user_id: decided.user_id, role: 'community_manager',
     space_id: decided.space_id, status: 'active', source: 'application',
     source_id: applicationId, granted_by: actorUserId })`, then a **second** audit row:
   `insertAuditEvent({ subject_type: 'role_grant', subject_id: grant.id, event: 'granted',
     subject_user_id: decided.user_id, actor_user_id: actorUserId, role: 'community_manager',
     space_id: decided.space_id, reason: input.reason, detail: null })`,
   then return `{ application: toManagerApplication(decided), grant: toGrantSummary(grant) }`.

   Add this comment above the `insertGrant` call, verbatim:
   ```
   // The grant is created here on purpose (05-RESEARCH.md Open Question 2). It is a
   // PREREQUISITE, not access: requireRole() re-evaluates the whole requirement list on
   // every call, and Phase 6 adds an active-billing requirement to that list. That is what
   // makes ROADMAP criterion 4 — "an approved applicant with no billing has NO manager
   // access" — hold without a schema change in Phase 6.
   ```

   If `insertGrant` fails with a unique violation on `uq_role_grants_live` (code `23505`), map it
   to `conflict('An active grant already exists for this user and space')`.

**3. `actOnGrant(deps, actorUserId, grantId, input: GrantActionRequest): ResultAsync<GrantActionResponse, AppError>`**

1. `findGrantById(grantId)`; null → `errAsync(notFound('Role grant'))`.
2. `requireReviewAuthority(actorUserId, { spaceId: grant.space_id ?? '*', targetRole: grant.role,
   action: input.action })`. Passing the target grant's **role** is what makes acting on an
   admin-tier grant super_admin-only (see `canReview` in `domain/authz/policy.ts`).
   When `grant.space_id` is null (a platform-wide super_admin grant) the space is `'*'`, which no
   `space_admin` grant can match — only a `super_admin` passes, which is correct.
3. Map the action to `(expected, next, endedAt)`:
   - `suspend`: `('active', 'suspended', null)`
   - `reinstate`: `('suspended', 'active', null)`
   - `revoke`: expected is the CURRENT status (`grant.status`), next `'revoked'`,
     endedAt `now.toISOString()` — a suspended grant must still be revocable.
4. `setGrantStatus(grantId, expected, next, endedAt)`. A `null` result →
   `errAsync(conflict('Grant is not in the expected state'))`.
5. `insertAuditEvent({ subject_type: 'role_grant', subject_id: grantId, event: input.action ===
   'suspend' ? 'suspended' : input.action === 'reinstate' ? 'reinstated' : 'revoked',
   subject_user_id: grant.user_id, actor_user_id: actorUserId, role: grant.role,
   space_id: grant.space_id, reason: input.reason, detail: null })`.
6. Return `{ grant: toGrantSummary(updated) }`.
