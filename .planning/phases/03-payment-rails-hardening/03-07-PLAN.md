<objective>
Take the webhook secret out of the URL, give the hosted-form path a real authenticity proof, make the route fail closed in production, and stop writing our own order id into the column that is supposed to hold a Green Invoice document id.

Purpose: SEC-03's constant-time comparison already exists (`greenInvoice.ts:313-319`) — the defect is the *transport*. The notify URL is registered as `.../api/payments/webhook?token=<secret>` (`:143`) and the verifier reads the query parameter **first** (`:314`). A shared secret in a URL leaks through referrers, proxy logs, browser history and Cloudflare's own request logging. PAY-07 has a quieter defect: `parseWebhookEvent` falls back to `documentId || orderId` (`:337`), so when Green Invoice's payload carries no document id, **our own order id is written to `payments.provider_id` as if it were a GI document** — and Phase 4's reconciliation would then match our id against itself and report zero mismatches while holding no document reference at all.

Output: header-only constant-time verification, a server-side document confirmation that replaces the URL secret for the hosted-form path, fail-closed production behaviour on both a bad secret and a database error, and a provider id that is either real or null.
</objective>

**Assumption A1, from `03-CONTEXT.md`** — GI's hosted form accepts no custom notify headers and signs no
payload. Basis: two independent in-repo assertions (the comment above and `webhook/route.ts:28-30`). It has
never been checked with Green Invoice. **This is why the fix is two factors rather than one swap**, and why
Task 3 puts the question on `GI-PRIME-CHECKLIST.md` so it stops being an assumption.

The second factor already has its machinery — `giRequest` (`:99-119`) authenticates every call with a JWT
minted from `GREENINVOICE_API_KEY_ID` / `GREENINVOICE_API_SECRET`, and `getPaymentStatus` (`:235-251`)
already fetches `/documents/{id}`. An attacker who guesses an order id cannot make Green Invoice produce a
document that does not exist.

The document-id defect:
```typescript
// services/payments/greenInvoice.ts:328-341
export function parseWebhookEvent(payload: Record<string, unknown>): PaymentWebhookEvent {
  const orderId = (payload.custom as string) || '';
  const documentId = (payload.id as string) || (payload.documentId as string) || (payload.paymentId as string) || '';
  return { type: 'payment.succeeded', paymentId: documentId || orderId, metadata: { orderId }, amount: 0 };
}                                             // ^^^^^^^^^^^^^^^^^^^^^^^^ silent fallback
// webhook/route.ts:108
const claimed = await markPaymentCompleted(payment.id, event.paymentId);   // <- writes it to provider_id
```
`markPaymentCompleted(paymentId, providerId?)` (`db.ts:545-565`) sets `provider_id` only when `providerId`
is truthy, so passing `null` is already safe and leaves the column untouched.

**There is no `transactions` table.** `payments` is the ledger: `payments.provider_id TEXT` holds the GI
document id and `payments.amount INTEGER` is in **agorot** (`20240101000000_initial_schema.sql:152,156`), so
₪50 is stored as `5000`. Confirmed independently by the Phase 4 planner. **Rename nothing.**

The database fail-open to close — `webhook/route.ts:70-89`:
```typescript
try { await createWebhookEvent({...}); }
catch (insertError) {
  // Unique-constraint race: a concurrent delivery won the insert.
  log.info('Concurrent webhook insert detected - treating as replay', {...});
  return NextResponse.json({ received: true, idempotent: true, replay: true });   // 200 on ANY db error
}
```
A genuine unique-constraint race is a replay and 200 is right. **Any other database error is not**, and
returning 200 tells Green Invoice to stop retrying — the delivery is lost. Postgres reports the unique
violation as SQLSTATE `23505`; plan 02.1-02 established this exact discrimination in
`db.ts`'s `recordUserVoteOnce`. Follow that precedent.

Untouchable in this plan: the atomic `markPaymentCompleted` claim at `:108` and its TOCTOU comment,
the replay short-circuit at `:62-69`, the token mint, the receipt email, and the `payment.failed` /
`refund.created` cases. Plan 03-02 already removed the treasury accrual and the vote-recording block.

/**
 * The Green Invoice document id from a notify payload, or null.
 *
 * Deliberately does NOT fall back to our own order id. `parseWebhookEvent` does,

export function extractDocumentId(payload: Record<string, unknown>): string | null {
  for (const key of ['id', 'documentId', 'paymentId'] as const) {

    if (typeof value === 'string' && value.length > 0) return value;

  return null;
}

4. **Add `confirmDocumentIssued`.** The second authenticity factor. It must never throw:

```typescript
/**
 * Ask Green Invoice whether this document exists, over the authenticated API.
 *
 * This is the authenticity proof for the hosted-form path, which cannot present
 * a header. An attacker who guesses an order id cannot make GI vouch for a
 * document that was never issued. Best-effort by design: on any transport or
 * auth failure this returns false, and the caller fails closed in production.

export async function confirmDocumentIssued(documentId: string): Promise<boolean> {
  if (!documentId) return false;
  try {
    const doc = await giRequest<{ id?: string }>(`/documents/${encodeURIComponent(documentId)}`, { method: 'GET' });
    return Boolean(doc);
  } catch (error) {
    logger.warn('Green Invoice document confirmation failed', { documentId });
    return false;
  }
}
```
