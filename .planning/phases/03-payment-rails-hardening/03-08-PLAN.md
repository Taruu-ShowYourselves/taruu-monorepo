<objective>
Make the payment idempotency key server-generated and deterministic, so a retry deduplicates instead of minting a second pending payment and a second Green Invoice form.

Purpose: `apps/web/src/app/api/payments/create/route.ts:77` currently reads

```typescript
const paymentIdempotencyKey = idempotencyKey || `${user.id}-${type}-${voteId || 'create'}-${Date.now()}`;
```

Both halves are exactly what SEC-04 forbids. The `Date.now()` suffix guarantees that every retry produces a
*different* key, so the `getPaymentByIdempotencyKey` lookup two lines below can never hit and the
`idempotency_key TEXT UNIQUE NOT NULL` constraint never does its job — a double-clicked create button yields
two pending rows and two hosted payment pages. The client override is worse: a caller can pin any key it
likes, including one belonging to somebody else's flow.

Output: a pure derivation module, a route that ignores whatever the client sent, and a unit test covering the
non-obvious part — that determinism must not lock a user out of ever creating a second vote with the same title.
</objective>

The required shape, from `REQUIREMENTS.md:20` and ROADMAP Phase 3 SC#4:
`{userId}:{type}:{voteId|optionId}` — server-generated, deterministic, never `Date.now()`.

**The gap that shape leaves, and which this plan must close.** After plan 03-02 the only payment type is
`vote_creation`, and a creation request carries **neither** `voteId` **nor** `optionId` — the vote does not
exist yet; it is created after the payment settles (`payments/return/page.tsx` → `POST /api/votes`). A key of
`{userId}:vote_creation:` with an empty third segment would be identical for every vote that user ever
creates. Since `idempotency_key` is `UNIQUE NOT NULL` and the route returns the existing row on a hit, the
user's **second** vote would silently return their **first**, already-completed payment and they could never
pay again. Determinism must not become a one-vote-per-lifetime lock.

The relevant database facts (`supabase/migrations/20240101000000_initial_schema.sql:148-168`):
```sql
amount          INTEGER NOT NULL,            -- agorot. ₪50 is stored as 5000.
status          payment_status DEFAULT 'pending',   -- pending | completed | failed | refunded
idempotency_key TEXT UNIQUE NOT NULL,
provider_id     TEXT,                        -- the GI document id (plan 03-07)
```
There is no `transactions` table; `payments` is the ledger.

The lookup helper (`apps/web/src/lib/supabase/db.ts`):
```typescript
export async function getPaymentByIdempotencyKey(key: string): Promise<Payment | null>
```

Hashing precedent — `apps/web/src/app/api/payments/webhook/route.ts:2,54` already uses Node's
`createHash('sha256')` on this runtime (`wrangler.jsonc:16` enables `nodejs_compat`). Use the same import.

Test coupling: plan 03-02 (wave 1) already removed `idempotencyKey: 'key-123'` from the request body of

```typescript
import { createHash } from 'crypto';
import type { Payment } from '@/lib/supabase/types';

/**
 * Server-side payment idempotency (SEC-04).
 *
 * The key is derived from the request's own identity and NEVER from the clock or
 * from anything the client sent. The old expression was
 *   `idempotencyKey || `${user.id}-${type}-${voteId || 'create'}-${Date.now()}``
 * which is defective twice over: the client could pin any key it liked, and the
 * clock suffix guaranteed every retry produced a fresh key, so the UNIQUE
 * constraint on payments.idempotency_key never once did its job.
 */

/** How many spent keys to walk before giving up. Bounded so a caller cannot spin. */
export const MAX_IDEMPOTENCY_CHAIN = 4;

export interface IdempotencyInput {
  readonly userId: string;
  readonly type: 'vote_creation';
  /** Present for flows that already have a vote. Creation has neither. */
  readonly voteId?: string | null;
  readonly optionId?: string | null;
  /** The creation draft's title - the only thing distinguishing two creations by one user. */
  readonly voteTitle?: string | null;
}

function shortHash(input: string): string {
  return createHash('sha256').update(input).digest('hex').slice(0, 16);
}

/**
 * `{userId}:{type}:{scope}` per SEC-04.
 *
 * `scope` is the vote or option when the flow has one. A CREATION request has
 * neither - the vote does not exist until the payment settles - so the scope is
 * a hash of the draft title. That keeps two different drafts distinct while
 * making a double-submitted identical draft collapse to one payment.
 */
export function derivePaymentIdempotencyKey(input: IdempotencyInput): string {
  const scope = input.voteId ?? input.optionId ?? shortHash(input.voteTitle ?? '');
  return `${input.userId}:${input.type}:${scope}`;
}

/**
 * The next key after a SPENT one.
 *
 * A completed or failed payment means this key is used up, but the user may
 * legitimately be creating another vote with the same title. Chaining off the
 * spent payment's id keeps the result deterministic - a double-submit at this
 * point still collapses to a single new payment - without reaching for a clock.
 */
export function deriveRetryKey(baseKey: string, spentPaymentId: string): string {
  return `${baseKey}:r${shortHash(`${baseKey}:${spentPaymentId}`)}`;
}

export type IdempotencyResolution =
  | { readonly kind: 'reuse'; readonly key: string; readonly existing: Payment }
  | { readonly kind: 'fresh'; readonly key: string }
  | { readonly kind: 'exhausted' };

/**
 * Walk the chain until we find an unused key, a reusable pending payment, or the bound.
 * `lookup` is injected so this is testable without a database.
 */
export async function resolveIdempotencyKey(
  lookup: (key: string) => Promise<Payment | null>,
  input: IdempotencyInput
): Promise<IdempotencyResolution> {
  let key = derivePaymentIdempotencyKey(input);

  for (let hop = 0; hop < MAX_IDEMPOTENCY_CHAIN; hop++) {
    const existing = await lookup(key);
    if (!existing) return { kind: 'fresh', key };
    if (existing.status === 'pending') return { kind: 'reuse', key, existing };
    key = deriveRetryKey(key, existing.id);
  }

  return { kind: 'exhausted' };
}
```
