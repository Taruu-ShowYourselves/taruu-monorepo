<objective>
Build the scheduler Green Invoice does not provide: a due-check that charges what is owed, walks the
retry ladder, enters grace, expires, and finalises cancellations — driven by a `CRON_SECRET`-guarded
route that runs on a trigger that already exists.

Purpose: `chargeToken()` is a one-shot off-session charge, so "₪50/month" is Taruu's scheduler or it
is nothing. And `apps/web/wrangler.jsonc:58` records that Cloudflare's schedules API rejected this
account's cron list behind an account-level gate, so this cannot assume a new monthly slot. The
resolution recorded in plan 06-01 is a due-check that is safe to invoke at any frequency, reached
from the one trigger that is live. MGR-03's exactly-once guarantee is inherited from plan 06-06's
`applyChargeForPeriod` rather than re-implemented here.

Output: one use-case, one cron route, a five-line change to the worker dispatcher, one test file.
</objective>

const CRON_SECRET = process.env.CRON_SECRET;
export async function POST(request: NextRequest) {
  const authHeader = request.headers.get('authorization');
  if (!CRON_SECRET) return NextResponse.json({ error: 'Cron endpoint not configured' }, { status: 503 });
  if (!authHeader || !secureEqual(authHeader, `Bearer ${CRON_SECRET}`))
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
  ...
}
export async function GET() { return NextResponse.json({ status: 'ok', endpoint: '…' }); }

```ts
const CRON_ROUTES: Record<string, string> = {
  '*/15 * * * *': '/api/cron/verification-notifications',
  '0 * * * *':    '/api/cron/resolve-votes',
  '*/10 * * * *': '/api/cron/mint-nfts',
  '0 */6 * * *':  '/api/cron/knesset-agenda',
};
async scheduled(event, env, ctx) {
  const path = CRON_ROUTES[event.cron];
  if (!path) return;
  const origin = env.NEXT_PUBLIC_APP_URL || 'https://taruu.co.il';
  const request = new Request(`${origin}${path}`, {
    method: 'POST', headers: { authorization: `Bearer ${env.CRON_SECRET ?? ''}` },
  });
  ctx.waitUntil(handler.fetch(request, env, ctx));
}
```

Create `apps/web/src/server/app/billing/renew.ts`.

Header comment, verbatim intent: "The renewal scheduler (MGR-03, MGR-04). Green Invoice has no
subscription object, so this is the entire recurring-billing engine. It is a DUE-CHECK, not a
monthly job: it selects only subscriptions whose time has come, so invoking it four times a day is
harmless and is the design — see `apps/web/docs/MANAGER-BILLING-TRIGGER.md` and the Cloudflare
account-level cron gate at `apps/web/wrangler.jsonc:58` that made a dedicated monthly slot
unavailable. Exactly-once is inherited from `applyChargeForPeriod`, which claims the charge row
before it calls the provider; nothing here adds a second, weaker guard."

```ts
export interface RenewalDeps { now?: () => Date; batchLimit?: number }

export function runManagerRenewals(deps: RenewalDeps): ResultAsync<RenewalRunResponse, AppError>;

/** Exported for testing one subscription in isolation. */
export function processDueSubscription(
  deps: RenewalDeps,
  subscription: ManagerSubscription
): ResultAsync<{ outcome: string; transitioned: boolean }, AppError>;
```

`runManagerRenewals`:
1. `now = deps.now?.() ?? new Date()`; `limit = deps.batchLimit ?? 100`
2. `listDueSubscriptions(now.toISOString(), limit)`
3. Process each **sequentially** — not `Promise.all`. Green Invoice is a single account with an
   in-memory cached JWT; hammering it in parallel buys nothing and risks rate limits. Sequential
   also keeps the log readable when something goes wrong at 03:00.
4. **Collect per-subscription failures instead of propagating them.** One dead subscription must not
   abort the batch and leave every later one unprocessed for another six hours. Log each with the
   subscription id and continue. This mirrors `processVoteResolutions`, which returns an `errors`
   array rather than throwing.
5. Return the tallies.

`processDueSubscription` switches on `deriveDueAction(toDueSubscription(subscription), now)`:

- **`none`** ⇒ no-op.

- **`charge`** ⇒ resolve the payment method (`findPaymentMethodById`; missing or non-`active` ⇒
  treat as a failed charge with `failureKind: 'hard'`, because there is nothing to charge and no
  retry will fix it). Period: for `chargeKind: 'renewal'` use `computeNextPeriod` from the current
  period; for `'retry'` reuse the **current** period — a retry pays for the period that failed, not
  for a new one. Then `applyChargeForPeriod(...)`, and:
  - `already_claimed` ⇒ count it in `skippedAlreadyClaimed`, transition nothing. Another run is
    mid-flight. Add a comment: this branch is the exactly-once guarantee being observed, not an
    error.
  - `succeeded` ⇒ `transitionSubscription(status, 'charge_succeeded')`, then
    `setSubscriptionStatus(id, status, 'active', { current_period_start, current_period_end,
    next_charge_at: current_period_end, failed_attempts: 0, grace_until: null })`, an audit event
    with `event: 'charge_succeeded'`, and **no** notification (plan 06-03's `noticeForTransition`
    returns `null` for a routine renewal — call `notifyBillingTransition` anyway and let it decide,
    so the "which transitions notify" policy stays in one place).
  - `failed` ⇒ `transitionSubscription(status, 'charge_failed')` (`active → past_due`,
    `past_due → past_due`), `setSubscriptionStatus` with `failed_attempts: n + 1` and
    `next_charge_at: nextRetryAt(firstFailureAt, n + 1)`, an audit event with the failure code, and
    `notifyBillingTransition('charge_failed', { retryAt })`. `firstFailureAt` is `now` on the first
    failure and the existing schedule anchor afterwards — derive it from the current
    `next_charge_at` minus the previous offset, or store it in the audit `detail`; pick one and say
    which in the summary.

- **`enter_grace`** ⇒ `transitionSubscription('past_due','entered_grace')`,
  `setSubscriptionStatus(id, 'past_due', 'grace', { grace_until: graceUntil(firstFailureAt),
  next_charge_at: null })`, audit `entered_grace`, notify. **Access is still granted here** —
  `isBillingActive` returns true for unlapsed grace. That is deliberate and must be commented,
  because it looks like a bug to anyone skimming.

- **`expire`** ⇒ `transitionSubscription('grace','expired')`,
  `setSubscriptionStatus(id, 'grace', 'expired', { ended_at: now, next_charge_at: null })`, audit,
  notify. **Access is lost here, and only here, on the failure path.** Do not revoke the role grant:
  the grant records approval, which is still true; `requireRole`'s billing requirement is what
  denies. Comment that.

- **`cancel`** ⇒ `transitionSubscription('active','cancelled')`,
  `setSubscriptionStatus(id, 'active', 'cancelled', { cancelled_at: now, ended_at: now,
  next_charge_at: null })`, audit, notify.

In every branch a `null` from `setSubscriptionStatus` means another run already applied the
transition. Count it and move on — it is not an error and must not be logged as one.

Never call `insertGrant` or `setGrantStatus` from this file. Never construct an idempotency key
here. Never import `supabaseAdmin` or `@/services/greenInvoice`.
