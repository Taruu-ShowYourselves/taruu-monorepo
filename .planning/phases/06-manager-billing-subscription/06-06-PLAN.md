<objective>
Ship the entry point of the subscription: an approval-gated checkout that creates a `pending`
subscription and a Green Invoice hosted card-setup page, and an idempotent webhook that activates it
— or rejects it — exactly once.

Purpose: this is where issue #79's first two acceptance criteria become real. Criterion 1 ("a
successful ₪50 payment without approval does not grant manager access") holds because checkout
refuses to start without an active `community_manager` grant, and because no line in this plan calls
`insertGrant`. Criterion 3 ("duplicate renewal events do not duplicate invoices, charges, or role
transitions") holds because the charge row is claimed under a `UNIQUE` idempotency key before the
provider is ever called, and because the status transition is a guarded `.eq('status', expected)`
update whose null result is treated as "already done".

Output: one shared charge path, two use-cases, two routes, one test file.
</objective>

Create `apps/web/src/server/app/billing/charge.ts` — the **only** place in the codebase that turns
"this subscription owes money for this period" into a charge row and a provider call. Both the
activation path (plan 06-06) and the renewal path (plan 06-07) go through it, so there is one
definition of exactly-once rather than two that drift.

Header comment, verbatim intent: "Claim, charge, record (MGR-03). The charge row is INSERTed under
its deterministic idempotency key BEFORE the provider is called. If the insert loses the unique
race, the provider is not called at all and the winner's row is returned — that, and not a
mutex or a check-then-act, is what makes a replayed or concurrent event produce exactly one charge
and one document. Green Invoice has no idempotency of its own to lean on here."

```ts
export interface ChargeDeps { now?: () => Date }

export type ChargeOutcome =
  | { kind: 'already_claimed'; charge: ManagerSubscriptionCharge }
  | { kind: 'succeeded'; charge: ManagerSubscriptionCharge; documentId: string | null }
  | { kind: 'failed'; charge: ManagerSubscriptionCharge; failureCode: string;
      failureKind: 'soft' | 'hard' | 'unknown' };

export function applyChargeForPeriod(
  deps: ChargeDeps,
  params: {
    subscription: ManagerSubscription;
    chargeKind: 'initial' | 'renewal' | 'retry';
    attempt: number;
    periodStart: Date;
    periodEnd: Date;
    tokenId: string;
    client: { name: string; email: string };
    description: string;   // Hebrew
  }
): ResultAsync<ChargeOutcome, AppError>;

/**
 * The hosted-form path: the money has ALREADY moved and Green Invoice has already
 * issued the document. This records that fact idempotently — it never calls the
 * provider. Used by activation, where the first ₪50 is collected by the hosted
 * page rather than by an off-session charge.
 */
export function recordExternalCharge(
  deps: ChargeDeps,
  params: {
    subscription: ManagerSubscription;
    periodStart: Date;
    periodEnd: Date;
    providerChargeId: string | null;
    providerDocumentId: string | null;
  }
): ResultAsync<ChargeOutcome, AppError>;
```

`applyChargeForPeriod`, in this exact order:

1. `key = buildChargeIdempotencyKey(subscription.id, params.periodStart, params.attempt)`
2. `claimCharge({ subscription_id, idempotency_key: key, kind, attempt, period_start, period_end,
   amount_agorot: subscription.price_agorot, status: 'claimed' })`
3. **If `claimed === false`, return `{ kind: 'already_claimed', charge }` and STOP.** Do not call
   the provider. Put a comment on this branch saying so — it is one `if` and it is the requirement.
4. `chargeSavedCard({ tokenId, amountAgorot: subscription.price_agorot, description, client,
   idempotencyKey: key })`
5. `completeCharge(charge.id, …)` with the success or failure detail and `chargedAt = now`
6. Return `succeeded` or `failed`

`recordExternalCharge` is steps 1–3 with `chargeKind: 'initial'`, `attempt: 1`, then
`completeCharge` straight to `succeeded` with the supplied provider ids. Same claim, no provider
call.

Neither function transitions the subscription and neither writes an audit event — the caller owns
that, because activation (`pending → active`) and renewal (`active → active`, next period) are
different transitions and burying them here would hide the state machine inside a payment helper.
Say that in a comment so the next reader does not "helpfully" add it.

Never import `supabaseAdmin` here, never import `@/services/greenInvoice` directly (go through
`@/services/billing/greenInvoice`), and never build an idempotency key inline.

**`activate.ts`** — `handleBillingWebhook(deps, request: Request, rawBody: string):
ResultAsync<{ received: true; idempotent?: boolean }, AppError>`.

1. Parse the JSON body; derive the event id exactly as the vote webhook does — the provider's own
   id when present, otherwise `gib_{subscriptionId}_{sha256(rawBody).slice(0,16)}`.
2. `getWebhookEventByEventId`. A `processed` row ⇒ return `{ received: true, idempotent: true }`
   immediately. Otherwise `createWebhookEvent({ provider: 'green_invoice', … })`, and treat a throw
   from that insert as a concurrent delivery: return `{ received: true, idempotent: true }` and let
   the winner do the work.
3. `parseBillingWebhook(payload)`. No `subscriptionId` ⇒ `notFound('Subscription')`.
4. `findSubscriptionById`. Null ⇒ `notFound('Subscription')`.
5. Status is already `active` ⇒ mark the webhook event processed and return
   `{ received: true, idempotent: true }`. This is the second replay guard and it is the one that
   survives a provider that changes its event id between deliveries.
6. Status is not `pending` ⇒ `conflict(...)`.
7. **No `paymentTokenId`**, or the payload indicates failure ⇒ transition `pending → rejected`:
   `transitionSubscription('pending','rejected')`, `setSubscriptionStatus(id,'pending','rejected',
   { ended_at: now })`, an audit event, and `notifyBillingTransition('rejected', …)`. Return
   `{ received: true }`. **Do not touch the role grant** — it was never activated by billing and
   billing does not revoke it.
8. Otherwise: `insertPaymentMethod({ user_id, provider_token_id: facts.paymentTokenId, brand, last4 })`,
   `attachPaymentMethod`, then `recordExternalCharge(deps, { subscription, periodStart, periodEnd,
   providerChargeId: facts.chargeId, providerDocumentId: facts.documentId })` with the period from
   `computeInitialPeriod(now)`.
9. `transitionSubscription('pending','activated')`, then `setSubscriptionStatus(id, 'pending',
   'active', { current_period_start, current_period_end, next_charge_at: current_period_end,
   failed_attempts: 0, payment_method_id })`. **A `null` result means another delivery already
   activated it — return `{ received: true, idempotent: true }`, not an error.**
10. `insertSubscriptionEvent({ event: 'activated', from_status: 'pending', to_status: 'active',
    charge_id, actor_user_id: null })`, then `notifyBillingTransition('activated', …)`.
11. `updateWebhookEventStatus(eventId, 'processed')`.
