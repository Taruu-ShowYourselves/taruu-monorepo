<objective>
Build the check that says whether the money and the database agree: a two-directional diff between
Green Invoice's settled documents and the internal `manager_subscription_charges` rows, reported
with an explicit open-mismatch count.

Purpose: MGR-05 requires reconciliation to zero open mismatches, and issue #79's Risks section says
to "fall back to manual invoice/reconciliation and keep roles inactive on ambiguous payment state".
Both of those need a check that can actually be run and whose output a human can act on. Green
Invoice has no subscription object and therefore no subscription-level statement — so this compares
documents to charge rows, which is the only join the two systems share.

Output: a pure diff with tests, one adapter addition, one use-case, one cron route, one worker
dispatch entry, one route test.
</objective>

Create `apps/web/src/server/domain/billing/reconcile.ts` — pure, no IO, no `neverthrow`.

Header comment, verbatim intent: "Two-directional reconciliation (MGR-05). It compares and it
reports. It has no authority to move money, change a subscription's state, or activate a role — if
it did, a bug in this file could grant access, and the whole point of the check is that it is the
thing you trust when you do not trust the rest.

`providerVerifiable: false` is a first-class outcome, not an error. If Green Invoice's document list
cannot be retrieved for the window, the provider→internal direction is genuinely unknown, and a
report that quietly said `openMismatches: 0` would be worse than useless — it would be a false
all-clear on the one number anyone reads."

```ts
export interface ProviderDocument {
  documentId: string;
  amountAgorot: number;      // caller converts from ILS
  issuedAt: string;
}

export interface ReconcileInput {
  windowStart: string;
  windowEnd: string;
  internal: Array<{
    id: string;
    status: 'claimed' | 'succeeded' | 'failed';
    amountAgorot: number;
    providerDocumentId: string | null;
  }>;
  provider: ProviderDocument[];
  /** False when the provider's documents could not be listed for this window. */
  providerVerifiable: boolean;
}

export function reconcileCharges(input: ReconcileInput): ReconciliationReport & { notes: string[] };
```

Implementation: filter internal to `status === 'succeeded'`; index the provider list by
`documentId`; walk internal for `missing_provider` and `amount_mismatch`; then, **only when
`providerVerifiable`**, walk the provider list for `missing_internal`. `openMismatches` is
`mismatches.length`. Push a note when `providerVerifiable` is false stating which direction was not
checked and why the zero is partial.

Every mismatch's `detail` is a sentence a human can act on — which charge, which document, which two
amounts — not a code.

Then create `apps/web/src/server/domain/billing/reconcile.test.ts` covering `<behavior>`. The
`providerVerifiable: false` test is the one that matters most: assert that `missing_internal` never
appears and that `notes` is non-empty.

```ts
export interface ProviderDocumentListing {
  documents: ProviderDocument[];
  /** False when this account/endpoint cannot enumerate documents for a window. */
  verifiable: boolean;
  note?: string;
}

/**
 * List settled documents in a window. TWO MODES, on purpose:
 *
 *  A. If Green Invoice exposes a document search on this account (see
 *     06-01-SUMMARY.md), enumerate and return { verifiable: true }.
 *  B. If it does not, or the call fails, return { documents: [], verifiable: false }
 *     with a note. Reconciliation then reports the provider→internal direction as
 *     UNVERIFIED rather than as zero mismatches. A false all-clear on this number
 *     is the worst possible failure mode for a reconciliation check, so degrading
 *     loudly is the correct behaviour and not a shortcut.
 */
export async function listSettledDocuments(startIso: string, endIso: string): Promise<ProviderDocumentListing>;

/** Single-document lookup, used to verify one internal row's document id. */
export async function fetchDocument(documentId: string): Promise<ProviderDocument | null>;
```

Amounts come back from Green Invoice in ILS. Convert to agorot **here**, at the boundary, exactly as
plan 06-04 converted the other way — `Math.round(sum * 100)`, so a float never reaches the diff.

**Then** create `apps/web/src/server/app/billing/reconcile.ts`:

```ts
export interface ReconcileDeps { now?: () => Date; windowDays?: number }
export function runBillingReconciliation(
  deps: ReconcileDeps
): ResultAsync<ReconciliationReport & { notes: string[] }, AppError>;
```

1. Window: `windowEnd = now`, `windowStart = now - (deps.windowDays ?? 35) days`. Thirty-five, not
   thirty: a monthly cycle plus the retry ladder means a charge for last period can legitimately
   settle up to a fortnight late, and a 30-day window would report those as mismatches every time.
   Say that in a comment — it is the kind of off-by-a-few that produces a permanently red check
   everyone learns to ignore.
2. `listChargesInWindow(startIso, endIso)`.
3. `listSettledDocuments(startIso, endIso)`, wrapped with `ResultAsync.fromPromise`; a throw becomes
   `{ documents: [], verifiable: false, note }` rather than failing the run — a provider outage must
   still produce a report of the internal side.
4. `reconcileCharges({ windowStart, windowEnd, internal, provider, providerVerifiable })`.
5. Log at warn level when `openMismatches > 0`, with the count and the mismatch kinds — never with
   amounts, names or document ids.
6. Return the report.

This use-case performs **no writes**. No `setSubscriptionStatus`, no `completeCharge`, no
`insertSubscriptionEvent`, no `insertGrant`. Put that in the header comment as a rule, because the
first instinct on seeing a `missing_internal` row will be to create it, and creating a charge row
from a provider document is how a reconciliation script ends up granting someone access.
