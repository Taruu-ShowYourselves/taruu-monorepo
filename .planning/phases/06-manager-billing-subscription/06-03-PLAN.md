The locked policy (06-CONTEXT.md → Decisions → "Grace, retry and cancellation"):
- failed charge ⇒ `past_due`, access **retained**, retry scheduled
- retries at **+1, +3, +7 days** from the first failure of that period
- after the third failure ⇒ `grace`, access **retained**, `grace_until = firstFailure + 14 days`
- `grace_until` passes with no success ⇒ `expired`, access **lost**, terminal
- cancellation is **end-of-period**: `cancel_at_period_end = true`, state stays `active`, access to

- a super admin may `suspend` from `active`, `past_due` or `grace`, and `reinstate` back

Header comment, verbatim intent: "Billing arithmetic (MGR-04). Every function takes the current
instant as an argument, so the retry ladder and the grace deadline can be tested in milliseconds
rather than over a fortnight, and a renewal run can be replayed against a fixed clock. The constants
below are the documented policy — changing one changes what users were promised, so change it here
and nowhere else."

```ts
export const PERIOD_MONTHS = 1;
export const RETRY_OFFSETS_DAYS: readonly number[] = [1, 3, 7];
export const GRACE_DAYS = 14;

export interface Period { start: Date; end: Date }
export function computeInitialPeriod(activatedAt: Date): Period;
/** Chains from the PREVIOUS period's end, never from `now`. */
export function computeNextPeriod(previous: Period): Period;

/** null once RETRY_OFFSETS_DAYS is exhausted — the caller then enters grace. */
export function nextRetryAt(firstFailureAt: Date, attempt: number): Date | null;
export function graceUntil(firstFailureAt: Date): Date;

export interface BillingFacts {
  status: ManagerSubscriptionStatus;
  graceUntil: Date | null;
}
/** The predicate plan 06-05 wires into requireRole. */
export function isBillingActive(facts: BillingFacts | null, now: Date): boolean;

export interface DueSubscription {
  status: ManagerSubscriptionStatus;
  nextChargeAt: Date | null;
  currentPeriodEnd: Date | null;
  graceUntil: Date | null;
  failedAttempts: number;
  cancelAtPeriodEnd: boolean;
}
export type DueAction =
  | { kind: 'none' }
  | { kind: 'charge'; chargeKind: 'renewal' | 'retry'; attempt: number }
  | { kind: 'enter_grace' }
  | { kind: 'expire' }
  | { kind: 'cancel' };
export function deriveDueAction(sub: DueSubscription, now: Date): DueAction;
```

Month arithmetic: add one month, then clamp the day-of-month to the target month's last day, so
`2026-01-31 + 1 month = 2026-02-28`. JavaScript's `setMonth` overflows into the following month
instead — write the clamp explicitly and test it. Work in UTC throughout; do not add a timezone
library and do not depend on the host's zone.

`isBillingActive` consults `ACCESS_GRANTING_STATES` imported from `./subscription`, not a second
literal list, and additionally requires `graceUntil > now` for the `grace` state. A row whose grace
window lapsed but which the cron has not swept must **not** authorize. That is issue #79's
"ambiguous payment state leaves the role inactive" posture applied to the one place a stale row can
grant access it should not have.

`deriveDueAction` evaluates in this order, and the order is load-bearing:
1. terminal/inert (`cancelled`, `rejected`, `expired`, `suspended`) ⇒ `none`
2. `grace` past `graceUntil` ⇒ `expire`
3. `active` with `cancelAtPeriodEnd` and `currentPeriodEnd` passed ⇒ `cancel` — **before** any charge
   branch, so a cancelling subscription is never charged one last time
4. `past_due` with `failedAttempts >= RETRY_OFFSETS_DAYS.length` ⇒ `enter_grace`
5. `nextChargeAt` null or in the future ⇒ `none`
6. otherwise ⇒ `charge`; `chargeKind` is `'renewal'` from `active`/`grace` and `'retry'` from
   `past_due`; `attempt = failedAttempts + 1`
