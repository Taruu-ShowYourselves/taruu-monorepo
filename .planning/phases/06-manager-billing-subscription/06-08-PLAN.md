<objective>
Ship the two ways a subscription ends or pauses: a subscriber cancelling at the end of the period
they already paid for, and a super admin suspending access with a recorded reason — plus the
reinstatement that undoes the latter.

Purpose: MGR-04 requires cancellation and the grace policy to produce "documented, predictable
access outcomes" with the user notified on every change that affects access. MGR-02 requires that a
super admin can suspend "independently of billing, with a stored reason" — issue #79's exact words.
This plan is where the seven-state machine stops being a diagram and becomes something a human can
trigger.

Output: one use-case module, two routes, one test file.
</objective>

Create `apps/web/src/server/app/billing/cancel.ts`.

Header comment, verbatim intent: "Ending and pausing a subscription (MGR-02, MGR-04).

Two independent levers exist, and conflating them is the mistake to avoid:

  * Suspending the SUBSCRIPTION (here) denies access via `billing_inactive` and stops the renewal
    job from charging someone whose access is suspended.
  * Suspending the GRANT (Phase 5's `/api/admin/role-grants/[id]`) denies via `grant_suspended` and
    is entirely independent of billing — that is issue #79's 'suspend access independently of
    billing'.

Neither implies the other. An admin may use either or both, and each writes its own append-only
audit row."

Two exports:

```ts
export interface CancelDeps { now?: () => Date }

export function requestCancellation(
  deps: CancelDeps, userId: string, input: CancelSubscriptionRequest
): ResultAsync<CancelSubscriptionResponse, AppError>;

export function adminActOnSubscription(
  deps: CancelDeps, actorUserId: string, subscriptionId: string,
  input: AdminSubscriptionActionRequest
): ResultAsync<AdminSubscriptionActionResponse, AppError>;
```

**`requestCancellation`**, in order:
1. `findSubscriptionById(input.subscriptionId)`; null ⇒ `notFound('Subscription')`.
2. **`subscription.user_id !== userId` ⇒ `notFound('Subscription')`, not `forbidden`.** A 403 here
   tells a stranger that the id exists. Ownership comes from the verified session and never from the
   request body.
3. Status not in `active`, `past_due`, `grace` ⇒ `conflict('Subscription cannot be cancelled in its
   current state')`. Cancelling something already `cancelled` or `expired` is a no-op the caller
   should see, not a silent success.
4. Already `cancel_at_period_end` ⇒ return the current state with 200 rather than 409. Clicking
   "cancel" twice is not an error and should not read like one.
5. `transitionSubscription(status, 'cancellation_requested')` — the state does **not** move.
6. `updateSubscriptionSchedule(id, { cancel_at_period_end: true })`.
7. `insertSubscriptionEvent({ event: 'cancellation_requested', from_status: status,
   to_status: status, actor_user_id: userId, reason: input.reason ?? null })`.
8. `notifyBillingTransition('cancellation_requested', { accessUntil: current_period_end, … })`.
9. Return `{ subscription: toSubscriptionSummary(updated, null), accessUntil: current_period_end }`.

Add this comment above step 6, verbatim in substance: "End-of-period, not immediate. The user paid
for this period; taking access away the moment they click cancel would be taking money for nothing.
The flag is set here and `deriveDueAction` returns `cancel` once `current_period_end` passes, at
which point the renewal job finalises the transition. There is no proration and no partial refund,
and the notice says so."

**`adminActOnSubscription`**, in order:
1. `findSubscriptionById(subscriptionId)`; null ⇒ `notFound('Subscription')`.
2. `requireReviewAuthority(actorUserId, { spaceId: subscription.space_id,
   targetRole: 'community_manager', action: input.action })`. **After** the load (the space is
   needed) and **before** any write. Passing `targetRole: 'community_manager'` is what lets a
   `space_admin` act inside its own space while keeping admin-tier targets super-admin-only — that
   logic already lives in Phase 5's `canReview` and is not re-implemented here.
3. `suspend`: `transitionSubscription(status, 'suspended')` (legal only from `active`, `past_due`,
   `grace`); refusal ⇒ `conflict(reason)`. Then `setSubscriptionStatus(id, status, 'suspended',
   { suspended_reason: input.reason, next_charge_at: null })` — clearing `next_charge_at` is what
   stops the renewal job from charging a suspended person.
4. `reinstate`: legal only from `suspended`. `setSubscriptionStatus(id, 'suspended', 'active',
   { suspended_reason: null, next_charge_at: <current_period_end> })`. If `current_period_end` has
   already passed, set `next_charge_at` to `now` so the next run picks it up immediately rather than
   granting a free month.
5. A `null` from `setSubscriptionStatus` ⇒ `conflict('Subscription is not in the expected state')`.
6. `insertSubscriptionEvent({ event: 'suspended' | 'reinstated', from_status, to_status,
   actor_user_id: actorUserId, reason: input.reason })` — actor, timestamp and reason, which is
   MGR-02's requirement stated literally.
7. `notifyBillingTransition(...)`.
8. Return `{ subscription: toSubscriptionSummary(updated, null) }`.

Never import `supabaseAdmin`. Never call `setGrantStatus` or `insertGrant` — the role grant is
Phase 5's to move, and an admin who wants to revoke approval uses that endpoint.
