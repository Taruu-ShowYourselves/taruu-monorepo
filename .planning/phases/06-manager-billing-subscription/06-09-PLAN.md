<objective>
Give the approved manager a Hebrew, RTL screen that tells them the truth about their billing: what
state it is in, whether they currently have access, what happens next, and what they can do — pay,
or cancel at the end of the period.

Purpose: MGR-04 requires predictable, documented outcomes and notification on every access change;
a screen that contradicts the email is worse than no screen. MGR-01's constraint reappears here in a
UI form — the panel must render `accessActive` as the server computed it and must never derive
access from a status string, because a client that decides access will eventually disagree with
`requireRole` and the disagreement will be silent.

Output: a pure view-model with tests, a presentational component, a stylesheet, and the wiring into
the screen Phase 5 already built.
</objective>

Create `apps/web/src/app/[locale]/settings/community-manager/billing-panel-model.ts` — a plain `.ts`
module so vitest collects its tests. No React import, no `fetch`, no DOM.

Header comment, verbatim intent: "The billing panel's decisions, extracted from the component
because `apps/web/vitest.config.ts` runs in `environment: 'node'` and never collects `.tsx`. This
module is unit-tested; `BillingPanel.tsx` renders what it returns and decides nothing.

`accessBadge` is derived from the server's `accessActive` field and NEVER from `status`. The server
already ran `isBillingActive` — the same predicate `requireRole` consults — and a client that
recomputes it will eventually disagree with the enforcement point without anyone noticing."

```ts
export const BILLING_STATUS_LABELS_HE: Record<ManagerSubscriptionStatus, string>;

export type BillingPrimaryAction =
  | 'subscribe' | 'resume_checkout' | 'update_payment' | 'cancel' | 'none';

export interface BillingPanelModel {
  statusLabel: string;                       // Hebrew
  tone: 'neutral' | 'ok' | 'warn' | 'error';
  accessBadge: { granted: boolean; label: string };
  priceLabel: string;                        // e.g. '₪50 לחודש'
  detailLines: string[];                     // Hebrew, already formatted
  primaryAction: BillingPrimaryAction;
  primaryActionLabel: string | null;
  /** Shown before the cancel request is sent. States the date and the no-refund rule. */
  cancelConfirmation: string | null;
}

export function buildBillingPanelModel(
  response: ManagerBillingStatusResponse,
  locale?: string
): BillingPanelModel;
```

Dates format as Hebrew day-month-year via `Intl.DateTimeFormat('he-IL', …)`; pass the locale in so
the function stays deterministic under test. Amounts format from `priceAgorot`.

Two pieces of copy carry a promise and must be exact in substance:
- the `cancelConfirmation` string names the date access runs until **and** says there is no partial
  refund, before the user confirms rather than after
- the `past_due` and `grace` copy says access **continues** and names what happens next; a manager
  whose card expired should not read something that sounds like they have already lost access

The `suspended` case offers no payment CTA at all. Paying does not lift a suspension, and offering
the button would take money for nothing.

Then create `apps/web/src/__tests__/services/billing-panel-model.test.ts` covering every case in

the `status: 'active'` + `accessActive: false` divergence, and a loop over all eight statuses
asserting no returned string matches `/₪\s*6|מנוי חבר|membership/`.

Create `BillingPanel.tsx` — a client component that fetches, renders the model, and performs the two
actions.

Header comment, verbatim intent: "Presentational. Every decision — label, tone, which action to
offer, what the cancel confirmation says — comes from `buildBillingPanelModel`. This file must

Behaviour:
- On mount, `fetch('/api/manager-billing?spaceId=' + encodeURIComponent(spaceId))`; hold
  loading / error / loaded states. A non-2xx renders a Hebrew RTL error with a retry, never a raw
  status code or an English string.
- Render `buildBillingPanelModel(response)`: the status label, the access badge, the price, the
  detail lines, and the charge history (date, amount, and a receipt link when `documentId` is
  present).
- `subscribe` / `resume_checkout` ⇒ `POST /api/manager-billing/checkout` then
  `window.location.assign(checkoutUrl)`. On 403 render the Hebrew "not approved" message and link to
  the application form above; on 409 re-fetch rather than showing an error, since the state simply
  moved on.
- `update_payment` ⇒ the same checkout call. The hosted form is how a card is replaced; there is no
  separate card-update surface in this phase, and a comment should say so rather than leaving the
  reader hunting for one.
- `cancel` ⇒ show `model.cancelConfirmation` and require an explicit confirm before
  `POST /api/manager-billing/cancel`, then re-fetch.
- Every button disables while its request is in flight, so a double click cannot fire two requests.

Never render `paymentMethod.last4` without its brand and without a masking prefix (`•••• 1234`).
Never render a subscription id, a charge id, an idempotency key or a token. Never call
`isBillingActive` or import anything from `@/server/**` — this is client code and the server modules
must not be reachable from it.

Create `BillingPanel.module.css` using design tokens only (`var(--color-*)`, `var(--space-*)`,
`var(--text-*)`), RTL-aware (logical properties or `flex-row-reverse`), with a visual treatment per
tone. No hex colours, no `px` literals outside a border width.
