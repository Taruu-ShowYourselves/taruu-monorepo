<objective>
Create the persistence and contract foundation for manager billing: four tables, real
`SELECT`-only RLS on top of the transport Phase 5 built, their TypeScript `Database` entries, and
the Zod contract module every route and use-case in this phase imports.

Purpose: MGR-02 demands eight explicit states with recorded transitions; MGR-03 demands
server-generated idempotency keys, exactly-once charges and no stored raw card data. Both are
enforced here in the schema rather than left to application discipline — a `UNIQUE` idempotency
key, a partial unique index that permits at most one *succeeded* charge per period, a `NOT NULL`
foreign key from subscription to role grant, and a `CHECK` on `last4` that a card number cannot
satisfy. Every later plan compiles against the types and contracts created here, so this plan is
the interface definition for the phase.

Output: one SQL migration, one contracts module, two shared constants, and the `Database` type
entries that make `supabaseAdmin.from('manager_subscriptions')` typecheck.

Create `supabase/migrations/20260803000001_manager_billing.sql`.

Open with a header comment stating these five decisions and their reasons:

1. **TEXT + CHECK, never `CREATE TYPE ... AS ENUM`.** Same reason Phase 5 gave: `ALTER TYPE ... ADD
   VALUE` is transaction-hostile, a CHECK edit is not. `payment_type` in the initial schema is the
   counterexample — a two-value native enum that cannot be extended cheaply, which is one reason
   subscription charges do not ride the `payments` table.
2. **Billing attaches to an approved grant; it never creates one.** `manager_subscriptions.role_grant_id`
   is `NOT NULL REFERENCES role_grants(id)`. There is no schema shape in which a successful charge
   produces access — issue #79 acceptance criterion 1, enforced by the database rather than by
   review discipline.
3. **Exactly-once is enforced by indexes, not by application care.** `idempotency_key` is `UNIQUE`
   across the charges table (claim-before-charge), and a partial unique index permits at most one
   `succeeded` charge per `(subscription_id, period_start)` — so a replayed provider event cannot
   produce a second settled charge or a second document even if every application guard failed.
4. **No card data.** The only card artefact stored is Green Invoice's own token id. `last4` is
   `CHECK (last4 ~ '^[0-9]{4}$')`, which a PAN cannot satisfy. There is no column for a card number,
   a CVV, or a raw provider payload.
5. **SELECT-only RLS, `TO authenticated`, service-role writes.** Identical to Phase 5. Adding an
   INSERT or UPDATE policy would create a second, weaker write path.

**The read-scope helper.** Charges carry no `space_id`, so their policy needs a subscription lookup.
Do it inside a `SECURITY DEFINER` function for exactly the reason Phase 5 gave for
`can_admin_space`: a policy subquery would otherwise evaluate the referenced table's own policies,
which is subtle at best and recursive at worst.

```sql
CREATE OR REPLACE FUNCTION public.can_read_manager_subscription(p_subscription_id UUID)
RETURNS BOOLEAN
LANGUAGE sql
STABLE
SECURITY DEFINER
SET search_path = public
AS $$
  SELECT EXISTS (
    SELECT 1 FROM public.manager_subscriptions s
    WHERE s.id = p_subscription_id
      AND (s.user_id = public.user_id() OR public.can_admin_space(s.space_id))
  );
$$;

COMMENT ON FUNCTION public.can_read_manager_subscription(UUID) IS
  'True when the JWT subject owns the subscription or administers its space. SECURITY DEFINER so a '
  'policy on manager_subscription_charges resolves the owning subscription without re-entering that '
  'table''s own policies — the same anti-recursion break as can_admin_space().';
```
