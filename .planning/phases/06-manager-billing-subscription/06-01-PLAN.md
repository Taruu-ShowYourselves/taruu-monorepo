  <decision>
How does `/api/cron/manager-renewals` get invoked in production, given that Cloudflare's schedules
API rejected this account's cron list behind an account-level gate and only `0 */6 * * *` is live?
  </decision>
  <context>
Green Invoice has no subscription object, so Taruu owns the scheduler. A monthly charge needs
*something* to fire. `wrangler.jsonc:58` records that adding cron expressions failed at deploy;
the four-cron block is commented out and only the 6-hourly knesset trigger survives.

The framing that dissolves most of the problem: **a renewal job does not need a monthly trigger.**
It needs to run *often enough* and charge only what is due. If the route selects
`WHERE next_charge_at <= now() AND status IN ('active','past_due','grace')`, then invoking it four
times a day is harmless — three of the four runs find nothing — and it buys four retry windows a
day instead of one. That turns "we need a new monthly cron slot" into "we need the existing
trigger to reach a second route", which is a five-line change to `worker.ts` and needs no gate.

Whichever option is chosen, two things are non-negotiable: the route is guarded by `CRON_SECRET`
with `secureEqual` like every other cron route here, and it is safe to invoke at any frequency
because the due-check plus the per-period idempotency key make a second invocation a no-op.
  </context>
  <options>
    <option id="option-a">
      <name>Fan the existing 6-hourly trigger out to multiple routes (recommended)</name>
      <pros>
Needs no Cloudflare gate resolution and no dashboard access — it ships today. Widens
`CRON_ROUTES` to `Record&lt;string, string[]&gt;` and appends `/api/cron/manager-renewals` to the
existing `0 */6 * * *` entry, leaving `/api/cron/knesset-agenda` exactly as it is. Four runs a day
means four retry opportunities, which makes the +1/+3/+7-day retry ladder land close to its
intended times rather than up to 24h late. The due-check makes the extra runs free.
      </pros>
      <cons>
Couples two unrelated jobs to one trigger — a change to the knesset cron's schedule silently moves
billing. Mitigated by a comment in `worker.ts` and by the due-check making the exact time
irrelevant. Also: the whole thing still depends on that one trigger continuing to work.
      </cons>
    </option>
    <option id="option-b">
      <name>Resolve the Cloudflare account cron gate and add a dedicated slot</name>
      <pros>
The clean answer. A dedicated `0 3 * * *` trigger, one job per cron, no coupling, and it unblocks
the three other crons (`verification-notifications`, `resolve-votes`, `mint-nfts`) that are
currently not running in production at all — which is a real latent problem this repo has
independent of billing.
      </pros>
      <cons>
Depends on a Cloudflare account-level capability nobody here has confirmed can be turned on, and on
dashboard access. If it cannot be resolved, the phase is blocked on an external party. Unknown
lead time.
      </cons>
    </option>
    <option id="option-c">
      <name>External scheduler (GitHub Actions `schedule:`) POSTing the route</name>
      <pros>
Independent of Cloudflare entirely. Needs only the app URL and `CRON_SECRET` as a repository secret,
not the `CLOUDFLARE_API_TOKEN` that has had CI deploy broken since 2026-07-28.
      </pros>
      <cons>
Moves money-critical scheduling outside the runtime that owns the app. GitHub's `schedule:` is
best-effort and skews under load. Puts a live production secret into GitHub Actions. Adds a second
place to look when a renewal does not happen.
      </cons>
    </option>
