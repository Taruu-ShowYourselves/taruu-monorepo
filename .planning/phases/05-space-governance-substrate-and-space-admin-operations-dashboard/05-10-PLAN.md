```ts
/**
 * The seam between the review decision and whatever payment rail exists.
 *
 * The locked product decision (05-CONTEXT.md) is that the ₪50 creation fee is
 * charged when a proposal is approved, not when it is submitted. The
 * card-on-file rail that can actually capture money off-session is phase 3
 * (PAY-06) and has not shipped. So approval calls this port; today's
 * implementation records a deterministic pending obligation against the
 * submitter, and when PAY-06 lands its token charge replaces the
 * implementation without decide-proposal.ts changing at all.
 */
export const CREATION_FEE_AGOROT = 5000;   // ₪50, matching CREATE_VOTE_COST

export interface CreationFeeCharge {
  paymentId: string;
  /** 'captured' once PAY-06 lands; 'obligation' with today's rails. */
  outcome: 'captured' | 'obligation';
}

export interface CreationFeePort {
  charge(cmd: {
    submitterUserId: string;
    voteId: string;
    amountAgorot: number;
  }): ResultAsync<CreationFeeCharge, AppError>;
}
```

`apps/web/src/server/infra/payments/creation-fee.ts` — the implementation available today:
- Idempotency key is generated server-side and deterministically, per SEC-04: `` `${submitterUserId}:${voteId}:vote_creation` ``. Never `Date.now()`. The `payments.idempotency_key` unique constraint is what makes a retried approval reuse the original row rather than creating a second obligation.
- Look up by idempotency key first; if a row exists, return it with its existing outcome. That is what makes step 5 of `decide-proposal.ts` safe to retry after a lost concurrency race.
- Otherwise insert `{ user_id, type: 'vote_creation', amount: CREATION_FEE_AGOROT, currency: 'ILS', status: 'pending', vote_id, idempotency_key, metadata: { chargedAt: 'approval', phase: '05', note: 'capture pending PAY-06' } }` and return `{ paymentId, outcome: 'obligation' }`.
- Map a database failure to `paymentInvalid('התשלום נכשל')` rather than `dbError`, so the decide use-case can surface the UI's charge-failure copy instead of a generic 500. Comment the reason.
- Export `createCreationFeePort(): CreationFeePort` so the decide use-case receives it through `deps` and tests can substitute a failing one.

Write a prominent header comment listing exactly what changes when PAY-06 lands: this file's `charge` body, and nothing else. Also state plainly what today's implementation does and does not do — it records that ₪50 is owed and does not move money — so nobody reads `outcome: 'captured'` into it.
