```ts
/**
 * Deterministic decision. The prior-state guard and the space predicate live
 * in the same UPDATE statement, so two concurrent decisions cannot both win:
 * the loser gets zero rows and a 409, never a second publication.
 */
export function transitionProposal(
  scope: SpaceScope, voteId: string, prior: 'in_review', next: 'active'|'pending'|'rejected'|'changes_requested'
): ResultAsync<VoteRow, AppError> {
  const q = supabaseAdmin
    .from('votes')
    .update({ status: next, updated_at: new Date().toISOString() })
    .eq('id', voteId)
    .eq('municipality_id', scope.municipalityCode)
    .eq('status', prior)
    .select()
    .maybeSingle()
    .then(({ data, error }) => { if (error) throw error; return data; });

  return ResultAsync.fromPromise(q, (c) => dbError('votes.transition', c))
    .andThen((row) => row
      ? okAsync(row)
      : errAsync<VoteRow, AppError>(conflict(
          'ההצעה כבר הוכרעה על ידי מנהל אחר. רעננו את הרשימה כדי לראות את המצב העדכני.'
        )));
}
```

Also note the database backstop — the partial unique index `uq_space_proposal_single_approval` on `space_audit_log` means even a code path that somehow bypassed this guard could not record a second approval for the same vote.

Also export `setContentModeration` is **not** in this file — that belongs to plan 05-06's `space-member.repo.ts`. Keep this module to the two decision functions so the two plans do not collide on one file.

Create `apps/web/src/server/app/space-admin/decide-proposal.ts` with `import 'server-only';`.

The guard order is fixed and must be implemented exactly, because each step exists to make the next one's failure unambiguous:

1. `authorize(session, rawSpaceId, capabilityFor(cmd.decision))` → scope. Approving needs `proposal.approve`; rejecting and returning-for-changes need `proposal.reject`.
2. `findProposalInScope(scope, voteId)` → `null` means either "no such vote" or "a vote in another space", and both return `forbidden()` with **no reason**. Never `notFound`.
3. Pure domain guards, in this order:
   - `reviewerMayDecide({ submitterId: row.creator_id, reviewerId: scope.userId })` → `forbidden('הצעה שהגשתם — ההכרעה שמורה למנהל אחר.')`. This one **may** carry a reason: it discloses nothing the caller does not already know, since they are the submitter. Note that in a comment so the no-reason rule does not look violated by accident.
   - `isDecidableFrom(row.status)` → otherwise `conflict('ההצעה כבר הוכרעה על ידי מנהל אחר. רעננו את הרשימה כדי לראות את המצב העדכני.')`.
4. `resolveDecisionTarget(cmd.decision, new Date(row.start_date), now)` → the next status.
5. `transitionProposal(scope, voteId, 'in_review', next)` — the authoritative guard. Zero rows is the 409.
6. `insertAuditRow({...}).map(() => decided)` — inside the same Result chain, **before** the success `map`, so a failed audit write fails the request:
```ts
insertAuditRow({
  space_id: scope.spaceId,
  actor_user_id: scope.userId,
  action: auditActionFor(cmd.decision),      // proposal.approved | .rejected | .changes_requested
  object_type: 'vote',
  object_id: voteId,
  prior_state: { status: row.status },
  new_state: { status: next },
  reason: cmd.reason,
})
```
Add a comment: the audit write is not fire-and-forget. If it fails the decision fails, because SPACE-04 says every decision writes an immutable row and a published-but-unaudited vote would break that.

Leave a clearly marked seam for plan 05-10, which inserts the ₪50 creation charge **between steps 4 and 5** for the approve branch only — that is, after `resolveDecisionTarget` has computed the next status and *before* `transitionProposal` publishes. Write the marker as the line immediately above the `transitionProposal` call:
```ts
// 05-10 inserts the creation-fee charge here, ahead of the transition, so an
// approval either charges and publishes or does neither. Do not reorder.
```
The placement is load-bearing and easy to get backwards: the marker belongs **before** step 5, not between 5 and 6. A marker after the transition would yield publish-then-charge, which is exactly what the approve dialog promises will not happen (`אף סכום לא נגבה` on a failed charge), and 05-10 Task 3 asserts the ordering by comparing line numbers.
