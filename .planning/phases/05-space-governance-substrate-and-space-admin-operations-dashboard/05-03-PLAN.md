In `apps/web/src/server/domain/votes/vote.ts`:

1. Add the allow-list — an allow-list, never a deny-list, so a status invented later is invisible by default:
```ts
/**
 * The only statuses a vote may be shown at under a public read path.
 * Allow-list on purpose: a status added in future is invisible until someone
 * deliberately adds it here.
 */
export const PUBLIC_VOTE_STATUSES = ['pending', 'active', 'ended', 'resolving', 'resolved'] as const;
export type PublicVoteStatus = (typeof PUBLIC_VOTE_STATUSES)[number];
```
`'failed'` is deliberately **out**. It marks a vote whose NFT resolution failed, and since `getVotesByMunicipality` carries no status predicate today, such a vote is visible now and stops being visible after this change. That is a real narrowing of the public surface, it follows from the locked allow-list, and it is intended — note it in the SUMMARY so a later reader does not "restore" it as a bug fix.

`'pending'` is **in** the allow-list, deliberately. It means "approved and scheduled, not yet open" — never "awaiting approval" — and `/he/votes` shows scheduled votes today. The security goal of this plan is excluding the four *review* states (`draft`, `in_review`, `changes_requested`, `rejected`), which this allow-list still does; dropping `pending` at the same time would be an unrelated behaviour change to a live public surface. Write that sentence as a comment above the constant so nobody "tightens" it later.

One list, therefore, for both jobs: it is the default filter when no status is supplied *and* the validation set for an explicitly supplied one. There is no second `PUBLIC_FILTERABLE_VOTE_STATUSES` constant — two nearly-identical allow-lists is exactly how one of them drifts.

export function normalizeStatusFilter(status: string | null): PublicVoteStatus | null {

}

`normalizeStatusFilter(...)` is already nested inside the object literal passed to `parse(...)`, which *is* normalise-then-validate: the raw parameter never reaches the schema. Do not restructure this into two statements, and above all do not switch to a throwing `ListQuerySchema.parse(...)`. `parse(Schema, input)` comes from `@/server/http/respond` and returns `Result<T, AppError>`, mapping a failure to a 400; it is the universal idiom in this repo, and there are zero throwing `Schema.parse(` call sites in `apps/web/src` or `packages/shared/src`. Replacing it would drop this route out of the Result monad the whole server layer is built on and turn a malformed `?municipality=` from a clean 400 into an unhandled `ZodError` — a 500.

**The only change in this file is the schema.** `ListQuerySchema`'s `status` becomes `z.enum(PUBLIC_VOTE_STATUSES).optional()`, widening it from today's hardcoded `z.enum(['pending', 'active', 'ended'])`. No `.nullable()` is needed — the call site already coalesces `null` to `undefined`.

Add the ordering comment shown above at the call site if it is not already there.
