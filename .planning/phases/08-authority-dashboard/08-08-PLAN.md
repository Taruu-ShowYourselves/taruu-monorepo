<objective>
Ship AUTH-04 and AUTH-06's write path: an authority publishes a versioned official response on a
vote, revises or retracts it without ever overwriting the prior text, and tracks targets whose state
changes are recorded as new versions carrying no legal claim.

Purpose: ROADMAP success criterion 3 — "official responses are append-only and versioned; every
revision retains its author, timestamp, and prior text rather than overwriting it" — and criterion 5
— "response deadlines and escalations exist as workflow states with recorded transitions; they carry
no legal claim." Plan 08-04 made overwriting physically impossible; this plan is where the product
behaviour that depends on it lives.

Output: two use-case modules, three routes, two test files.
</objective>

Create `apps/web/src/server/app/authority/responses.ts`.

Header comment:

> AUTH-04. There is no update path here and there never will be. A revision is
> `insertResponseVersion` with `version = current + 1`; the previous row keeps its body, its author
> byline and its timestamp forever. `authority-content.repo.ts` exports no update or delete
> function, and the `official_responses_append_only` trigger raises if anyone reaches past it.
> Retraction is a version with `publication_state = 'retracted'` — the retracted text stays
> readable, because "we said this and then withdrew it" is a different public fact from "we never
> said it".

`publishOfficialResponse(userId, voteId, input)`:
1. `resolveAuthorityScope(userId)` — supplies `municipalityId` and `organizationId`, and has already
   proven the organization is verified. Any active representative may author; authorship is not
   restricted to `authority_admin` (a municipal spokesperson is rarely the account holder).
2. Load the vote (`id, municipality_id, title`) and:
   - `notFound('Vote')` when missing
   - `forbidden('cross_municipality')` when `vote.municipality_id !== ctx.municipalityId` — the
     explicit cross-municipality check success criterion 2 demands, on the one route where a
     client-supplied id crosses a scope boundary. Test it.
3. `findResponseVersions(voteId, ctx.organizationId)` → `nextVersion = (versions[0]?.version ?? 0) + 1`.
4. Resolve the author's display name and the organization's `display_name_he` **now**, and write both
   onto the row (`author_display_name`, `author_org_name_he`). Comment: these are snapshots, not
   joins — AUTH-05 requires the byline to survive the author being offboarded or their user row
   deleted, and a join would render "unknown" the day either happens.
5. `insertResponseVersion({ vote_id, organization_id, municipality_id, version: nextVersion,
   body_he, publication_state, revision_note, author_user_id: userId, author_display_name,
   author_org_name_he })`. A CONFLICT from the repo (23505 on the version index) means two authors
   raced: return it as 409 so the client re-reads and retries against the new head. Do **not** retry
   in a loop — a silent retry can publish a revision against text the author never saw.
6. Return the `OfficialResponseSchema` shape: `current`, `revisionCount`, `history` (all versions,
   newest first), `isOfficialAuthority: true`, `organizationNameHe`.

`getResponseHistory(userId, voteId)`: scope, cross-municipality check, `findResponseVersions`,
same response shape; `null` when there is none.

Route `apps/web/src/app/api/authority/votes/[id]/response/route.ts`: `POST` (publish, rate-limited
by `authorityWriteLimiter`) and `GET` (history). Thin shells. **No `PATCH`, no `PUT`, no `DELETE`
export** — and state in a comment that their absence is the API-level expression of append-only,
not an omission.

Create `apps/web/src/server/app/authority/commitments.ts`.

Header comment:

> AUTH-05 and AUTH-06. A target ("יעד") is an append-only version chain keyed by `thread_id`. A
> state change is a new version, so "who moved this to escalated, when, and what it said before" is
> always answerable — including after that person is offboarded.
>
> **These are tracking states, not legal states.** `workflow_state` and `target_date` carry no
> obligation and create no claim. No column is named deadline, due, obligation, sla or breach; no
> Hebrew string in the UI says or implies otherwise; and `AUTHORITY_TRACKING_DISCLAIMER_HE` is
> rendered on every page that shows them (asserted by the copy guard in plan 08-11). If a future
> requirement wants enforceability, that is a legal product decision and a different data model —
> issue #76 puts legal filing explicitly out of scope.

`listCommitments(userId)` → `resolveAuthorityScope` → `listCurrentCommitments(ctx.organizationId)`,
mapped to `CommitmentVersionSchema[]`, newest transition first.

`upsertCommitment(userId, input)`:
1. `resolveAuthorityScope(userId)`.
2. **New target** (`threadId` absent): `threadId = crypto.randomUUID()`, `version = 1`. Reject
   `workflow_state` values that make no sense as an opening state — only `draft` and `published` are
   valid for version 1 (`validation(['workflowState: a new target opens as draft or published'])`).
3. **New version** (`threadId` present): `findCommitmentThread(threadId)`;
   `notFound('Commitment')` when empty; `forbidden('cross_municipality')` unless
   `head.organization_id === ctx.organizationId`; `version = head.version + 1`. Carry forward
   `title_he`, `detail_he`, `vote_id` and `target_date` from the head when the input omits them, so a
   pure state transition does not silently blank the target's own description.
4. When `voteId` is supplied, verify that vote belongs to `ctx.municipalityId`; otherwise
   `forbidden('cross_municipality')`.
5. Resolve and snapshot `author_display_name`.
6. `insertCommitmentVersion(...)`; a CONFLICT from the repo (23505 on `(thread_id, version)`) → 409.
7. Return the new version.

`getCommitmentThread(userId, threadId)` → scope, ownership check, `findCommitmentThread`, full
history newest-first.

Routes:
- `GET /api/authority/commitments` → `listCommitments`
- `POST /api/authority/commitments` → `UpsertCommitmentRequestSchema` → `upsertCommitment`
  (rate-limited by `authorityWriteLimiter`)
- `GET /api/authority/commitments/[id]` → `getCommitmentThread` (id is the `thread_id`)
- `POST /api/authority/commitments/[id]` → `upsertCommitment` with `threadId` taken from the **path**,
  overriding any body value — the path is the authority on identity

No `PATCH`, `PUT` or `DELETE` exports on either route.
