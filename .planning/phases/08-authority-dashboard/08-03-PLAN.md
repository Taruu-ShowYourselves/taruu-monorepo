Create `apps/web/src/server/app/authority/require-authority.ts`.

Header comment, stated plainly because it is the phase's central safety property:

> Authority authorization (AUTH-01, AUTH-02). This module holds NO authorization logic of its own —
> every decision is delegated to `requireRole()` in `@/server/app/authz/require-role`, exactly as
> `requireReviewAuthority()` does. There is one enforcement point in this codebase and this is not
> it; this is a composition of it.
>
> `resolveAuthorityScope()` exists so that no route ever reads a municipality from a request. A
> representative's municipality is a property of their grants, not of what their browser sent.
> Plan 08-13 greps every file under `src/app/api/authority/` for a client-supplied municipality and
> fails the phase if it finds one.

```ts
export interface AuthorityContext {
  userId: string;
  municipalityId: string;
  organizationId: string;
  role: 'authority_admin' | 'authority_rep';
  grant: GrantFacts;
}

/** Derive the caller's own authority scope. THE entry point for every authority route. */
export function resolveAuthorityScope(userId: string): ResultAsync<AuthorityContext, AppError>;

/** Authorize the caller for a KNOWN municipality (e.g. re-checking a stored row's scope). */
export function requireAuthority(userId: string, municipalityId: string): ResultAsync<AuthorityContext, AppError>;

/** Representative management — authority_admin only. */
export function requireAuthorityAdmin(userId: string, municipalityId: string): ResultAsync<AuthorityContext, AppError>;
```

Implementation notes:

- `requireAuthority` mirrors `requireReviewAuthority`: try `requireRole(userId, 'authority_admin',
  municipalityId)`; on a **FORBIDDEN** failure only, fall back to `requireRole(userId,
  'authority_rep', municipalityId)`; any other error kind propagates unchanged.
- Both `requireAuthority` and `requireAuthorityAdmin` then call
  `findOrganizationByMunicipality(municipalityId)` and fail
  `forbidden('organization_not_verified')` when it is null. Because that repo function already
  filters `verification_status = 'verified'`, an unverified *and* a suspended organization take the
  same branch — which is the intended behaviour and must be asserted by two separate tests so a
  future refactor cannot collapse the distinction silently.
- `resolveAuthorityScope` calls `listActiveGrants(userId)` (Phase 5), filters to the two authority
  roles, prefers `authority_admin`, and then delegates to `requireAuthority(userId, grant.space_id)`
  so the verified-organization check runs through exactly one code path. If no authority grant
  exists, `forbidden('no_authority_grant')`.
- Never call `supabaseAdmin` directly from this module. Only `role.repo` and `authority.repo`.

Then create the colocated `require-authority.test.ts` covering every `<behavior>` case, mocking
`@/server/infra/supabase/role.repo` and `@/server/infra/supabase/authority.repo` with `vi.mock` and
