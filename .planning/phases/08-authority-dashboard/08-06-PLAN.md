```ts
/**
 * Representative invitation tokens (AUTH-02).
 *
 * A token is 32 random bytes, base64url. Only sha256(token) is persisted
 * (authority_rep_invitations.token_hash, UNIQUE). The raw token leaves this process
 * exactly once, inside the invite response's acceptUrl, and is never logged, never
 * written to an audit detail blob, and never returned by any repository function.
 *
 * A plain hash rather than an HMAC is deliberate and sufficient: the token is 256
 * bits of CSPRNG output, so there is no dictionary to attack and a keyed hash would
 * only add a secret to rotate.
 */
export const INVITATION_TTL_DAYS = 14;

export function generateInvitationToken(): string;           // crypto.getRandomValues(32) → base64url
export async function hashInvitationToken(token: string): Promise<string>;  // sha256 hex

export type InvitationDecision =
  | { ok: true; invitation: InvitationFacts }
  | { ok: false; reason: 'invalid' };

/**
 * ONE failure reason on purpose. Unknown, expired, revoked and already-accepted must
 * be indistinguishable to the caller — a distinct "expired" response is a probe that
 * confirms a guessed token once existed.
 */
export function decideInvitationAcceptance(
  invitation: InvitationFacts | null,
  now: Date
): InvitationDecision;
```

`InvitationFacts` is `{ id, organizationId, municipalityId, email, status, expiresAt }` — a narrow
projection, not the row type, so this module has no database coupling.

assertion across all four failure results.

  simply, resolve scope and assert `ctx.role === 'authority_admin'` via `requireAuthorityAdmin`;
  either way the municipality is the caller's own, never an argument.
- `generateInvitationToken()` → `hashInvitationToken()` → `insertInvitation({ organization_id,
  municipality_id, email, invited_role: 'authority_rep', token_hash, invited_by: userId,
  invited_by_name, status: 'pending', expires_at: now + INVITATION_TTL_DAYS })`. A 23505 on
  `uq_authority_invite_open` → `conflict('invitation_already_open')`.
- One audit row: `{ subject_type: 'authority_rep_invitation', subject_id: invitation.id,
  event: 'submitted', subject_user_id: null, actor_user_id: userId, role: 'authority_rep',
  space_id: ctx.municipalityId, reason: null, detail: { emailDomain: <domain part only> } }`.
  **Never** the full email and **never** the token or its hash in `detail`.
- Return `{ invitationId, email, expiresAt, acceptUrl }` where `acceptUrl` is
  `${NEXT_PUBLIC_APP_URL}/he/authority/invite?token=${rawToken}`. Comment: this is the only moment
  the raw token exists outside the CSPRNG call; it is not persisted and not logged.

`acceptInvitation(userId, { token })`:
- `hashInvitationToken(token)` → `findInvitationByTokenHash(hash)` →
  `decideInvitationAcceptance(facts, new Date())`. On `{ ok: false }` return
  `forbidden('invalid_invitation')` — one message for all four failure modes.
- `setInvitationStatus(id, 'pending', 'accepted', { acceptedBy: userId, acceptedAt: nowIso })`;
  `null` → `conflict('invitation_already_used')`.
- `insertGrant({ user_id: userId, role: 'authority_rep', space_id: invitation.municipality_id,
  status: 'active', source: 'authority_invitation', source_id: invitation.id, granted_by:
  invitation.invited_by })`. A 23505 on `uq_role_grants_live` means the user already holds a live
  grant there → success, reuse it.
- One audit row: `event: 'granted'`, `subject_type: 'role_grant'`, `subject_id` = the grant id,
  `subject_user_id` = userId.
- Note in a comment: acceptance does **not** verify that the accepting user's email matches the
  invited address. The token is the credential; requiring both would break the common case of a
  municipal employee whose Taruu account uses a personal address, and would add an email-enumeration
  surface. The invited address is retained on the row for the audit trail.

`setRepresentativeStatus(userId, grantId, { action, reason })`:
- `resolveAuthorityScope(userId)` and require `authority_admin`.
- `findGrantById(grantId)` → `notFound('Grant')` if missing.
- **Scope check, non-negotiable:** reject with `forbidden('cross_municipality')` unless
  `grant.space_id === ctx.municipalityId` **and** `grant.role` is one of the two authority roles.
  Without this, an authority admin of city A could pass a grant id belonging to city B. Add a test
  for exactly that.
- Refuse to act on the caller's own grant → `conflict('cannot_modify_own_grant')`, so an admin
  cannot lock themselves or the organization out in one click.
- Map: `suspend` → `setGrantStatus(id,'active','suspended', null)`; `reinstate` →
  `setGrantStatus(id,'suspended','active', null)`; `offboard` →
  `setGrantStatus(id,'active','revoked', nowIso)` (and also accept `'suspended' → 'revoked'`, since
  offboarding a suspended representative is a normal operation — implement as a two-attempt chain
  or by passing the row's current status as `expected`). A `null` result → `conflict('grant_state_changed')`.
- One audit row per action with the mandatory `reason`, `subject_type: 'role_grant'`.
- **Nothing else happens.** No response, target, snapshot or claim row is touched. Comment it, and
  the test asserts no content-repo function is imported by this module at all.
