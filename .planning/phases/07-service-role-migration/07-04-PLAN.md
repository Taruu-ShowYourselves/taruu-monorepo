<objective>
Move 66 of `db.ts`'s 114 exports into eight domain modules under `apps/web/src/lib/supabase/db/`,
leaving `db.ts` re-exporting them so all 62 importers keep working untouched.

Purpose: `db.ts` is 2441 lines and every wave-4 slice needs to edit it. Seven plans editing one
file serialize into seven waves and produce diffs nobody can review. After the split each slice owns
its own module exclusively, the seven run in one parallel wave, and a reviewer reads a 150-line
domain module instead of a diff against a 2441-line file.

This is a **pure move**. No signature changes, no behaviour changes, no client changes — every
function still calls `supabaseAdmin` exactly as it does today. Migration is wave 4's job. The proof
that this plan is correct is the test suite staying at its pre-split count.

Output: eight modules, and a `db.ts` that is 48 exports plus eight re-export lines.
</objective>

**Remaining in `db.ts` after this plan** (48 exports, plan 07-06's scope): push tokens (6), webhook

**How the resolution trick works.** `db.ts` stays a file in this plan and simply re-exports. In
plan 07-06 it is deleted and `db/index.ts` takes its place; because Node and TypeScript resolve
`@/lib/supabase/db` to `db/index.ts` when `db.ts` is absent, none of the 62 importers ever change.
Do not create `db/index.ts` in this plan — while `db.ts` exists, having both is ambiguous to
readers even though resolution prefers `db.ts`.

**Test contract.** `.planning/codebase/TESTING.md`: route tests do
`vi.mock('@/lib/supabase/db', () => ({ fnName: vi.fn(), … }))`, which replaces the whole module.
Re-exports are transparent to that. The suite must stay green at its current count — that is this
plan's only real proof. Baseline from `05-02-SUMMARY.md`: **827 passing across 67 files**, plus
whatever plan 07-03 added.
