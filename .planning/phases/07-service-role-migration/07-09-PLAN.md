**This slice's tables and their live policies:**

| Table | Policies | Owner column |
|---|---|---|
| `verification_runs` | `Users can view own verification runs` SELECT `USING (user_id = public.user_id())` | `user_id` |
| `verification_schedule` | `Users can view own verification schedule` SELECT — **via a subquery on `verification_runs`**, not a direct `user_id` match | (indirect) |
| `verification_attempts` | `Users can view own verification attempts` SELECT | `user_id` |
| `phone_verifications` | `Users can read own phone verification` SELECT `TO authenticated`; `Service role full access` `FOR ALL TO service_role` | `user_id` |

Two things to check before writing a line:

1. **`verification_schedule`'s policy is indirect** (`20240101000001_rls_policies.sql:92-100`). It
   matches through the parent run, so a schedule row is visible only when its run belongs to the
   caller. Read the exact expression; a swapped read that filters on the wrong column will return
   zero rows and look like a policy bug.
2. **`phone_verifications`'s own-row policy was corrected** by
   `20260628000002_fix_rls_user_id_helper.sql:28-33` from `auth.uid() = user_id` to
   `user_id = public.user_id()`. The **original file still shows the broken form** at
   `20250119000001_phone_verifications.sql:99-103`. Read the corrective migration, not the original —
   this exact confusion is what SEC-01 existed to fix.

**`db/verification.ts` exports** (10): getActiveVerificationRun, getVerificationRunById,
createVerificationRun, updateVerificationRun, getVerificationSchedule, getNextPendingCheckIn,
createVerificationScheduleItems, updateVerificationScheduleItem, createVerificationAttempt,
getUpcomingReminders.

`getUpcomingReminders()` takes **no parameters** — it sweeps every user's schedule for the reminder
cron. D2b consequence 1: there is no owner id to build a client from. It stays privileged and is
this module's clearest `@privileged`. Its caller is
`apps/web/src/app/api/cron/verification-notifications/route.ts`.

**The two phone routes**, whose privileged uses are the interesting part of this slice:

`apps/web/src/app/api/user/phone/send-code/route.ts` (4 references at L16, L122, L185, L199):
- L122 reads the caller's own `phone_verifications` row — an own-row read, candidate for migration.
- L185/L199 insert and update that row. `phone_verifications` has **no** INSERT or UPDATE policy for
  `authenticated`, only the `service_role` one. D2 keeps these privileged.
- The rate-limit RPCs (`can_send_phone_verification`, `record_phone_verification_send`) are
  `GRANT EXECUTE … TO service_role` (`20250119000001:288-293`). A rate limit the caller could
  execute as themselves is not a rate limit. Privileged, and say so.

`apps/web/src/app/api/user/phone/verify/route.ts` (5 references at L15, L127, L169, L194, L208):
- L127 reads the caller's own verification row — candidate.
- L169/L194 record an attempt and mark verified — privileged, no write policy.
- L208 writes `users` (`phone_verified`, or similar) — a system decision about a user's status, not
  a user edit. Privileged.

Both routes get a session via `getSessionFromRequest`, so `session.userId` is available for any read
that migrates.

Harness primitives from plan 07-03 are listed in `07-03-SUMMARY.md`; build against those signatures.
The `@privileged` and `PRIVILEGED:` formats are in `apps/web/docs/PRIVILEGED-ACCESS.md`.

Existing test to keep green: `apps/web/src/__tests__/api/phone-verification.test.ts`. It mocks
`supabaseAdmin`, so changing which client a route uses **will** change what it must mock. Update the
test's mocks; never weaken an assertion to make it pass.
