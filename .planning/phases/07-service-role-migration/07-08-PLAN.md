<objective>
Migrate the identity slice — `users`, `social_proofs`, `identity_documents`,
`identity_document_events` — onto the RLS-enforced transport, and prove it.

Purpose: this is the slice that holds who a person is. `identity_documents` stores an HMAC of an
Israeli ID number; `social_proofs` links a civic identity to social accounts. Today every one of
those reads runs on a key that bypasses RLS entirely.

Output: two `db/` modules migrated, two repos migrated, one RLS test file covering four tables.
</objective>

**This slice's tables and their live policies** (after plan 07-07's apply):

| Table | Policies | Owner column |
|---|---|---|
| `users` | `Users can view own profile` SELECT `USING (id = public.user_id())`; `Users can update own profile` UPDATE | `id` |
| `social_proofs` | `Users can view own social proofs` SELECT; `Users can delete own social proofs` DELETE | `user_id` |
| `identity_documents` | `Users can read own identity document` SELECT `TO authenticated` | `user_id` |
| `identity_document_events` | `Users can read own identity document events` SELECT `TO authenticated` | `user_id` |

Note `users` and `social_proofs` each have a **write** policy already (UPDATE and DELETE
respectively). Per D2 those writes may migrate. `identity_documents` has no write policy — its
upsert stays privileged.

**This slice's exports** (from `DB-ACCESS-CLASSIFICATION.md`; that document is authoritative — if it
disagrees with this table, follow it and say so in the summary):

`db/users.ts` (9): getUserById, getUserByEmail, getUserByGoogleId, getUserByDID, createUser,
updateUser, updateUserIdentityScore, getUsersByMunicipality, getVoteParticipantsWithEmails.

`db/social-proofs.ts` (5): getSocialProofsByUserId, getSocialProofByProvider, createSocialProof,
upsertSocialProof, deleteSocialProof.

**The three that must stay privileged, and why** — verify each by grepping callers rather than
trusting this list:

- `getVoteParticipantsWithEmails` — reads `user_votes` joined to *other* users' emails for
  notification fan-out. Cross-user by design. The most sensitive read in the codebase.
- `getUserByEmail` / `getUserByGoogleId` / `getUserByDID` — lookups **by** an identifier, run during
  sign-in when there is no session and possibly no row yet
  (`apps/web/src/app/api/auth/callback/route.ts`). D2b consequence 3.
- `getUsersByMunicipality` — cross-user by definition.

`identity.repo.ts` (7 references) — read it before deciding. `idHashClaimedByOther` deliberately
looks for *another* user's row: it is the ID-number collision check and is cross-user by design. It
stays privileged and is the clearest `@privileged` example in this slice.
`setUserIdentityVerifiedAt` writes `users.verification_status` as a system decision, not a user edit.

`user.repo.ts` — thin: `findUserById` wraps `getUserById` from `@/lib/supabase/db`. It probably needs
no change; confirm rather than assume.

The `@privileged` convention is defined in `apps/web/docs/PRIVILEGED-ACCESS.md` (plan 07-02). A bare
tag with no reason text fails the plan 07-15 guard.

`users` has only `email` as a NOT NULL column without a default
(`20240101000000_initial_schema.sql:24-47`), which is why the harness seeds `{ email }` and nothing
else.
