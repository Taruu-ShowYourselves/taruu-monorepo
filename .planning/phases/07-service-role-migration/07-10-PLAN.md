**This slice's tables and their live policies:**

| Table | Policies | Notes |
|---|---|---|
| `user_votes` | `Users can view own vote records` SELECT `USING (user_id = public.user_id())` — **that is the only one** | No INSERT, UPDATE or DELETE policy. Every ballot write stays privileged under D2. |
| `vote_options` | `Anyone can view vote options` SELECT, via a subquery on `votes` | Read is effectively public. The tally bump is a write with no policy. |

**`db/ballots.ts` exports** (8, from plan 07-04): incrementVoteOption, recordUserVote, getUserVote,
hasUserParticipated, `BallotInsertResult`, recordUserVoteOnce, getUserVotes, getUserVotesWithDetails.

**`db/stats.ts` exports** (6): countRegisteredUsers, countRegisteredUsersByMunicipality,
countUserVoteParticipations, countVotesCreatedByUser, getVotesCreatedByUser, getUserVoteStats.

`db/stats.ts` mixes two postures in one module and both must be handled explicitly:

- Per-user counts — `countUserVoteParticipations(userId)`, `countVotesCreatedByUser(userId)`,
  `getVotesCreatedByUser(userId)`, `getUserVoteStats(userId)`. Owner-parameter swaps under D2b.
  Careful: `countVotesCreatedByUser` and `getVotesCreatedByUser` read `votes` filtered by
  `creator_id`, and `votes` has a `Creators can view own votes` SELECT policy
  (`20240101000001:137-139`) keyed on `creator_id`, plus `Anyone can view active votes`
  (`status = 'active'`). A creator reading their own **draft** vote depends on the creator policy —
  check it resolves before swapping, or a creator's drafts silently vanish.
- Cross-user aggregates — `countRegisteredUsers()`, `countRegisteredUsersByMunicipality(code)`.
  `users` has **no** `USING (true)` policy, so an anon client returns 0 and a user-scoped client
  returns 1. `DB-ACCESS-CLASSIFICATION.md` section 3 decided their fate; follow it. If the decision
  was an aggregate `SECURITY DEFINER` function, plan 07-05 created it — use it. If the decision was
  "stays privileged", tag them.

**The participation contract that must not move** (Phase 02.1, commits in
`.planning/phases/02.1-participation-persistence/`):

- `recordUserVoteOnce` returns a `BallotInsertResult` and is idempotent by catching SQLSTATE `23505`
  and reading the row back. It inserts into `user_votes`, which has no INSERT policy → **privileged**.
- `recordUserVote` (the throwing variant) is still used by
  `apps/web/src/app/api/payments/webhook/route.ts:191` — a webhook, no session → **privileged**.
- `incrementVoteOption` calls the RPC `increment_vote_option` and falls back to a direct
  `vote_options` update. A tally bump is a write with no policy → **privileged**.
- `apps/web/src/__tests__/api/vote-participation.test.ts` is 693 lines / 30 tests and locks all of
  this in. It must pass **unmodified** except for mock declarations.

`apps/web/src/app/api/votes/[id]/participate/route.ts` has 2 `supabaseAdmin` references, both
reading `votes` (checking the vote is open). It holds a session. `votes` reads belong to plan 07-11's
catalogue module, so here only decide the route's own two reads and tag them.

Create `apps/web/src/__tests__/rls/ballots.rls.test.ts`. This is the phase's most important test
file; write it as if it is the only one that survives.

`describeRls`, never bare `describe`. Explicit `20_000` timeout on every network `it`.

**The seed needs three levels**, because a ballot cannot exist without a vote and an option:

1. Through `serviceClient`, insert one **active** vote and one **non-active** vote (needed for the
   `vote_options` subquery assertions), each with `creator_id` set to a throwaway user.
2. Insert a `vote_options` row for each.
3. Insert one `user_votes` row for A and one for B, **on the same vote**. Same-vote is the point:
   two ballots differing only by owner is precisely what the policy must separate. Two ballots on
   different votes could pass for the wrong reason.

Use `seedOwnedRows` for the `user_votes` pair with `ownerColumn: 'user_id'` so cleanup tracks them;
seed the votes and options directly through `serviceClient` and delete them in `afterAll` in FK-safe
order — `user_votes`, then `vote_options`, then `votes`.

The central assertion, written so its failure message is unmistakable:

```ts
it('user A cannot read user B’s ballot on the same vote', async () => {
  await expectCrossUserInvisible(env, 'user_votes', fx.userA.id, [ids.ballotA], [ids.ballotB]);
}, 20_000);
```

The write-denial assertions matter as much as the read ones, because they are the evidence for
decision D2's "writes stay privileged":

```ts
it('user A cannot insert a ballot directly — no INSERT policy exists', async () => {
  await expectUserWriteDenied(env, 'user_votes', fx.userA.id, {
    user_id: fx.userA.id, vote_id: seededVoteId, option_id: seededOptionId,

}, 20_000);
```

pass here would be the worst outcome in the phase: a green test claiming the ballot is secret while
proving only that an empty table is empty. Assert a **non-empty** `expectedVisibleIds` everywhere.

Run with credentials and record the count.
