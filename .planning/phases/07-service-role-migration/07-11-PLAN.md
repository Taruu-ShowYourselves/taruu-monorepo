<objective>
Move the public catalogue — `votes`, `vote_options`, `vote_sources`, `knesset_items`,
`knesset_rankings`, `municipalities` — off the service-role key and onto the anon client, and prove
both halves: anon can still read what is public, and cannot read what is not.

Purpose: these are the reads on unauthenticated pages. There is no user, so there is no user token
— which is exactly why they have been running on a key that bypasses RLS entirely. Today the
municipality directory page holds a handle that could read `identity_documents`. After this slice it
holds a handle that can read the six public tables and nothing else.

This slice is also the phase's guard against over-correction. Six of the fourteen `USING (true)`
policies are deliberately public; a phase that only ever asserts denial could "succeed" by breaking
every public page. `expectPublicReadWorks` exists for that.

Output: two `db/` modules migrated, two server-layer callers checked, one RLS test over five tables.
</objective>

**This slice's tables and their live policies:**

| Table | Policy | Verdict from 07-01 |
|---|---|---|
| `votes` | `Anyone can view active votes` SELECT `USING (status = 'active')`; `Creators can view own votes` SELECT `USING (creator_id = public.user_id())` | not a `USING (true)` — status-filtered |
| `vote_options` | `Anyone can view vote options` SELECT, via a subquery on `votes` | inherits the status filter |
| `vote_sources` | `vote_sources_public_read` SELECT `USING (true)` | KEEP — public citations |
| `knesset_items` | `knesset_items_public_read` SELECT `USING (true)` | KEEP — public record |
| `knesset_rankings` | `knesset_rankings_public_read` SELECT `USING (true)` | KEEP — public record |
| `municipalities` | `Anyone can view municipalities` SELECT `USING (true)` | KEEP — public directory |

**The status filter is the trap in this slice.** `votes` is *not* `USING (true)`. An anon client
sees only `status = 'active'` rows. Any surface that lists closed, resolved, or draft votes will go
blank if its read is naively swapped. Check each function's callers and what statuses they need:

- `getActiveVotes` / `getActiveVotesWithOptions` — active only. Safe for anon.
- `getVotesByMunicipality` — check whether the council page shows closed votes. If it does, anon
  returns fewer rows and the page silently loses history.
- `getVoteById` / `getVoteWithOptions` — a vote detail page must render a closed vote and say it is
  closed (plan 02.1-05 established that). Under anon, a closed vote is a 404. **These almost
  certainly stay privileged**; confirm against `DB-ACCESS-CLASSIFICATION.md` and the route
  behaviour, and record what you found.
- `findVoteByMunicipalityAndTitle` — an ingestion-side dedupe lookup, session-less and
  status-agnostic. Privileged.

**`db/votes.ts` exports** (13): getVoteById, getVoteWithOptions, getActiveVotes, getVotesByMunicipality,
getActiveVotesWithOptions, findVoteByMunicipalityAndTitle, upsertVoteSource, getKnessetItemByItemId,
upsertKnessetItem, getKnessetItemsByVoteIds, getKnessetRankingsByVoteIds, createVote, createVoteOptions.

Writes here — `upsertVoteSource`, `upsertKnessetItem`, `createVote`, `createVoteOptions` — have no
policy on any of these tables and are ingestion or creation paths. All privileged under D2.
`createVote` is user-initiated (a resident pays ₪50 to create one) but `votes` has no INSERT policy;
its tag should say that explicitly rather than lumping it with the ingestion writes.

**`db/municipality.ts` exports** (4): the three types plus `getMunicipalityProfile`, which calls the
RPC `municipality_profile_metrics`. Plan 07-02 determined whether that function is
`SECURITY DEFINER` and whether `anon` may execute it; follow that finding. An RPC executed by `anon`
against RLS-protected tables returns nothing unless it is `SECURITY DEFINER`, so guessing here
produces an empty municipality page.

**Public callers to sanity-check after migrating** (they render with no session):
