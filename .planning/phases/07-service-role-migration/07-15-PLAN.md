**`role.repo.ts`** (Phase 5 plan 05-03, 14 `supabaseAdmin` references) already carries a comment
saying its reads move onto `createUserScopedClient()` in Phase 7. Its exports:

```
findLiveGrant  listActiveGrants  findGrantById  insertGrant  setGrantStatus

listSubmittedApplications  decideApplication  insertAuditEvent  listAuditEvents
```

Phase 5's six policies (`05-02-SUMMARY.md`), all `FOR SELECT TO authenticated`, no write policies:

```
role_grants_select_own            USING (user_id = (SELECT public.user_id()))
role_grants_select_admin          USING ((SELECT public.can_admin_space(space_id)))
cm_applications_select_own        USING (user_id = (SELECT public.user_id()))
cm_applications_select_admin      USING ((SELECT public.can_admin_space(space_id)))
role_grant_events_select_own      USING (subject_user_id = (SELECT public.user_id()))
role_grant_events_select_admin    USING ((SELECT public.can_admin_space(space_id)))
```

**The recursion trap.** `findLiveGrant` is called by `requireRole`, which is the authorization
helper. If `findLiveGrant` runs on a user-scoped client, its query is filtered by
`role_grants_select_own` — which is fine — but `role_grants_select_admin` calls
`public.can_admin_space()`, a `SECURITY DEFINER` helper that itself reads `role_grants`. Phase 5 made
that helper `SECURITY DEFINER` with `SET search_path = public` precisely so evaluation cannot recurse
into `42P17`. Verify against the live database rather than reasoning about it: `05-04`'s
`role-tables.rls.test.ts` already exercises the admin path and re-throws `42P17` with a hint.

**The bootstrap trap.** `requireRole` is how the app decides whether someone is an admin. If the
lookup itself becomes RLS-filtered, an admin who cannot read their own grant cannot be an admin. The
own-row policy covers exactly that case, so it should work — but if it does not, `findLiveGrant`
stays privileged with a reason naming this, because an authorization check that can lock everyone out
is strictly worse than a privileged read.

**`apps/web/src/lib/supabase/index.ts`** (1 reference) re-exports `supabaseAdmin`. Decide whether the
barrel should keep re-exporting a privileged client at all, or whether importers should reach for
`@/lib/supabase/server` explicitly so a privileged import is visible at the import line. State the
decision; if the re-export goes, update whatever imports it (`grep -rn "from '@/lib/supabase'"`).

**The convention the guard enforces**, from `apps/web/docs/PRIVILEGED-ACCESS.md` (plan 07-02):

- File-level: any file importing `supabaseAdmin` contains a line beginning `PRIVILEGED:` followed by
  a reason.
- Function-level: inside `apps/web/src/lib/supabase/db/**`, any exported function whose body
  references `supabaseAdmin` carries an `@privileged` JSDoc tag with reason text on the same line.
- A bare `@privileged` with no reason is a failure, not a pass.

The starting population was 19 non-test source files (`07-CONTEXT.md`). After seven slices it will be
smaller. Derive the final list from the tree, not from that number.

Test conventions: `.planning/codebase/TESTING.md`. vitest 1.6.1, `environment: 'node'`, include glob
`src/**/*.test.ts`. The guard reads files from disk with `node:fs`; it must **not** import them,
because importing a route module pulls in Next.js runtime and env it does not need.

 *

 * If you are here because this test failed, that file explains what to write.
 */

```

Structure:

1. **Walk.** Recurse `apps/web/src`, collecting `.ts`/`.tsx` files, skipping `__tests__`,
   `node_modules` and any `.d.ts`. Resolve the root from `import.meta.url` or `process.cwd()` — the
   test must work from both the repo root and `apps/web`, since the repo runs vitest from both.
2. **Find privileged files.** A file is privileged when it imports `supabaseAdmin` — match the import
   statement, not any mention, so a comment referencing it (as `user-client.ts` does) is not counted.
3. **Assert the file-level marker.** Each privileged file must contain a line matching
   `/PRIVILEGED:\s*(.{20,})/`. The 20-character floor is what turns `PRIVILEGED: needed` into a
   failure.
4. **Assert against the allow-list.** Parse the markdown table in
   `apps/web/docs/PRIVILEGED-ACCESS.md` section 3 for file paths. Assert set equality in both
   directions and report the two differences separately, because they mean different things: a file

   A simple brace-free scan between export boundaries is sufficient and far more maintainable than a
   parser; say so in a comment so the next reader does not "upgrade" it to a TypeScript AST walk.

Failure messages must name names:

expect(

  `These files import supabaseAdmin with no PRIVILEGED: reason:\n  ${unjustified.join('\n  ')}\n` +
  `See apps/web/docs/PRIVILEGED-ACCESS.md.`

```

A guard whose failure reads `expected true to be false` is a guard the next person deletes.
