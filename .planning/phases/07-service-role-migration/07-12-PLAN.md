<objective>
Migrate the payments slice — `payments` and `entitlements` — onto the RLS-enforced transport, and
prove that user A cannot read user B's payment history.

Purpose: `payments` holds what a person paid, when, and against which provider transaction. It has
had an own-row SELECT policy since the initial schema and that policy has never once been evaluated,
because every read runs on the service-role key.

This slice contains the phase's canonical mixed-caller problem: several payment functions are called
from both a user route and a provider webhook. A function with one session-less caller cannot use a
user-scoped client. Plan 07-02 decided each case; this plan implements those decisions rather than
re-litigating them.

Output: two `db/` modules migrated, one repo checked, one RLS test over two tables.
</objective>

**This slice's tables and their live policies:**

| Table | Policy | Owner column |
|---|---|---|
| `payments` | `Users can view own payments` SELECT `USING (user_id = public.user_id())` | `user_id` |
| `entitlements` | `Users can view own entitlements` SELECT `USING (user_id = public.user_id())` | `user_id` |

Both are read-only for `authenticated`. Neither has an INSERT, UPDATE or DELETE policy, so **every
write in this slice stays privileged** under decision D2 — which is correct anyway, since payment
rows are written by settlement, not by users.

**`db/payments.ts` exports** (12, per plan 07-04): verifyPaymentCompleted, isPaymentAlreadyUsed,
getPaymentById, getPaymentByProviderId, getPaymentByIdempotencyKey, createPayment,
markPaymentCompleted, updatePaymentStatus, getLatestRefundablePayment, `RefundRequestResult`,
requestPaymentRefund, getUserPayments.

**`db/entitlements.ts` exports** (3): createEntitlement, getUserEntitlements, hasVoteEntitlement.

**The callers, and what they imply.** Grep before deciding, but the shape is:

- Session-less webhook path — `apps/web/src/app/api/payments/webhook/route.ts` and
  `apps/web/src/app/api/merch/webhook/route.ts`. Everything they call is privileged.
  `markPaymentCompleted` in particular is the atomic settlement claim that returns `Payment | null`,
  where `null` means "another delivery already won." An RLS-filtered version of that would report a
  lost race that never happened — a correctness bug, not just a permissions one.
- User routes with a session — `api/payments/[id]/status`, `api/payments/[id]/verify`,
  `api/payments/create`, `api/payments/refund`, `api/user/participations`,
  `api/user/treasury-contributions`.
- **Lookups by a non-owner identifier** — `getPaymentByProviderId(providerId)` and
  `getPaymentByIdempotencyKey(key)` take no user id at all. D2b consequence 1: there is no owner
  parameter, so they cannot migrate. Both are settlement-side anyway.

`getPaymentById(paymentId)` is the mixed-caller case `DB-ACCESS-CLASSIFICATION.md` section 3 was
required to resolve: its parameter is a payment id, not an owner id, and it is called from both a
user route and a webhook. Follow the classification's resolution — split into two exports, or keep
privileged — and do not invent a third option here.

`requestPaymentRefund` returns the `RefundRequestResult` string-literal union
(`'ok' | 'not_refundable' | 'already_requested'`), which
`apps/web/src/__tests__/api/payments-refund.test.ts` mocks by value. The union must not change.

`payment.repo.ts` imports from `@/lib/supabase/db` and wraps `assertPaymentUsable` in
`ResultAsync<…, AppError>`. Check `grep -c supabaseAdmin` — it is likely 0, in which case this file
is a no-op and should be recorded as one.

Harness primitives: `07-03-SUMMARY.md`. Tag formats: `apps/web/docs/PRIVILEGED-ACCESS.md`.
