Create `apps/web/docs/PRIVILEGED-ACCESS.md`. This is the MIG-03 contract, and it must be
mechanical, because plan 07-15 builds a test that enforces it and a convention a test cannot check
decays on the first hurried PR.

**Section 1 — why privileged access is legitimate here.** Two paragraphs. The goal is not zero
`supabaseAdmin` uses; it is that each remaining one is a visible, arguable exception. Name the four
legitimate categories from the roadmap's Framing: webhooks, cron routes, NFT minting, notification
fan-out — plus the fifth this codebase actually has, cross-user public aggregates.

**Section 2 — the two markers.** Define both precisely enough to grep for.

*File-level.* Every file that imports `supabaseAdmin` carries a block comment containing a line
starting `PRIVILEGED:` followed by a reason:

```ts
/**
 * PRIVILEGED: Green Invoice webhook. No session exists — the caller is the
 * payment provider, authenticated by a shared secret, not by a user cookie.
 * Reads and writes `payments` and `webhook_events` on behalf of nobody.
 */
import { supabaseAdmin } from '@/lib/supabase/server';
```

*Function-level.* Inside `apps/web/src/lib/supabase/db/**`, every exported function that still
touches `supabaseAdmin` carries an `@privileged` JSDoc tag with the reason on the same line:

```ts
/**
 * Records a processed webhook event.
 * @privileged webhook replay guard — no session; `webhook_events` is service-role-only
 */
export async function createWebhookEvent(/* … */) { /* … */ }
```

A bare `@privileged` with no text is a failure, not a pass. Say so.

**Section 3 — the allow-list.** A table of every file that will still import `supabaseAdmin` at the
end of this phase, drawn from Task 1's `system` rows, with columns: file, category (webhook / cron /
mint / fan-out / public-aggregate / infrastructure), and the one-line reason. `lib/supabase/server.ts`
is `infrastructure` — it defines the client. `lib/supabase/index.ts` re-exports it. This table is
what plan 07-15's guard test compares the source tree against, so it must be exact.

**Section 4 — the guard test contract.** Specify, in enough detail that plan 07-15 implements it
without a second design pass, what `apps/web/src/__tests__/lib/privileged-access.test.ts` asserts:

1. Enumerate every file under `apps/web/src` (excluding `__tests__`) that imports `supabaseAdmin`.
2. Every such file contains a `PRIVILEGED:` line with at least ~20 characters of reason after it.
3. Every file in the set appears in section 3's allow-list, and every allow-list entry still exists
   on disk — so both an unjustified addition and a stale allow-list entry fail.
4. For every file under `apps/web/src/lib/supabase/db/`, every exported function whose body
   references `supabaseAdmin` has an `@privileged` tag with a reason.
5. The failure message names the offending file and, where relevant, the function — a guard whose
   failure message is `expected true to be false` is a guard nobody fixes.

State that the test reads files from disk with `node:fs` and does not import them, because importing
a route module pulls in Next.js runtime and env it does not need.

**Section 5 — how to add a new privileged call site.** Four steps: write the reason, add the
`PRIVILEGED:` block, add the allow-list row, run the guard. Explicitly: if you cannot write the
reason, that is the signal the call site should not be privileged.

Write no code files in this task — this document specifies the test; plan 07-15 writes it.
