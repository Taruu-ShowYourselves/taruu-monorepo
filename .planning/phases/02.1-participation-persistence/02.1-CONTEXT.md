# Phase 02.1: Participation Persistence - Context

**Gathered:** 2026-08-02
**Status:** Ready for planning
**Source:** `.planning/v1.0-MILESTONE-AUDIT.md` P0 finding + owner decisions captured during `/gsd:plan-phase 02.1`

<domain>
## Phase Boundary

**Delivers:** a free vote that is actually recorded. The participation UI calls the server, the ballot lands in `user_votes`, the option tally and `participant_count` move, and the receipt states only facts the database row backs.

**Does NOT deliver:** any payment code, any chain write, any change to who is allowed to vote. The eligibility rule (`isEligibleToVote`) and the residency program are unchanged. Membership/pricing re-scoping belongs to the Phase 3 re-scope, not here.

**Why urgent:** this is live on taruu.co.il. Residents complete a vote, see `נחתם` and `✓ חתום בבלוקצ׳יין · בלתי ניתן לשינוי`, and nothing is stored. Every vote cast since `cfa5d25` (2026-07-29) is lost.
</domain>

<decisions>
## Implementation Decisions

### Receipt and seal — LOCKED: honest record now, chain later

- The blockchain-seal claim comes out. `mockHash()` (`ParticipationFlow.tsx:54-67`) is deleted, not repaired.
- `SealCard` and the `✓ חתום בבלוקצ׳יין · בלתי ניתן לשינוי` trust line (`ParticipationFlow.tsx:341-352`) are removed from the receipt stage. There is no `BLOCK` number, because there is no block.
- The receipt keeps its visual weight but shows only server-backed facts: the chosen option, cost `חינם`, a status word that is true, the server's `user_votes.id`, and the server's `created_at` timestamp — not a client `new Date()`.
- Status wording moves off `נחתם` (sealed/signed) to a recording word — `נרשם` or `נקלט`. Step 3's label `חתימה` (`STEPS`, `ParticipationFlow.tsx:34-38`) moves with it, as does the `שלב 03 · חתימה` kicker and the `הקול שלכם נחתם.` headline.
- Chain anchoring stays out of scope — it is BAG-02 / v2 (`REQUIREMENTS.md`, v2 section). Nothing in this phase should make a future chain write harder, but nothing here implements one.

### Token award — LOCKED: no tokens for free votes

- The 3-token mint at `participate/route.ts:190-194` is removed. Tokens were consideration for a ₪3 payment that no longer exists; minting them for free inflates supply against the existing סימנים economics.
- The `sendPaymentReceiptEmail` call at `:222-230` (`amount: 3`, `tokensEarned: 3`, `receiptUrl` pointing at `/receipts/{paymentTxId}`) is removed for the free path. There is no payment, so there is no payment receipt to email.
- `tokensEarned: 3` in the success response (`:253`) goes with it.

### Server contract — the payment shape is removed, not bypassed

- `POST /api/votes/[id]/participate` must accept `{ optionId }` alone. `paymentTxId` and `gpsCoordinates` stop being required (`route.ts:52-57`).
- `verifyPaymentCompleted` / `isPaymentAlreadyUsed` and the 402 branch (`:128-158`) come out of the free path.
- `recordUserVote` is called with `payment_id` omitted/null. This is already legal: `user_votes.payment_id` is `UUID REFERENCES payments(id) ON DELETE SET NULL` — nullable (`supabase/migrations/20240101000000_initial_schema.sql:236`).
- The per-vote GPS gate (`verifyCheckIn`, `:78-92`) comes out. Residency is verified **once** at `/verification`; the product has no per-vote GPS step, which is why the client never sends coordinates. Removing it is a deliberate restoration of the documented model, not a security relaxation — see the eligibility note below.
- The `qubikService.recordVote` call and its **hard 503** (`:170-185`) come out. Qubik is being dropped as the chain (project decision: chain = Solana, transparency-mirror only), and a dead chain service must never be able to reject a resident's vote.

### Eligibility — server must enforce what the client shows

- The client gates on `isEligibleToVote(user)` (`apps/web/src/lib/verification.ts:22` — `phase === 'completed'` OR `checkInsCompleted >= 1`).
- The server currently gates on `identity_score >= 40` (`route.ts:118-123`), a different rule.
- **Decision:** the server is the enforcement point and must apply the same rule the client shows. A client-side gate alone is not a gate. If the two rules cannot be reconciled inside this phase, the server keeps the stricter check and the planner flags the divergence explicitly — it must not silently drop the server check to match the client.

### Idempotency — lean on the database, not on application logic

- `user_votes` already carries `UNIQUE(user_id, vote_id)` (`initial_schema.sql:240`). A duplicate submit must surface as a handled unique-violation, not a 500 and not a second row.
- The existing `hasUserParticipated` pre-check (`route.ts:94-104`) stays as the fast path, but it is a check-then-act race and cannot be the only defence under double-click or retry.
- `incrementVoteOption` (`db.ts:987`) must only run on a genuinely new row — never on the duplicate path, or the tally drifts above the ballot count.

### ₪3 legacy — reconcile across the monorepo

- `packages/shared/src/constants/index.ts:6` still exports `VOTE_COST = 3`.
- Web no longer charges it, but mobile still renders `עלות הצבעה: ₪3` (`apps/mobile/app/vote/[id].tsx:340`) and `apps/web/src/services/payments/greenInvoice.ts:34` still imports it as `VOTE_PARTICIPATION_AMOUNT`.
- `CREATE_VOTE_COST = 50` is unaffected and must stay — vote creation is still paid and its flow is the one money path that works end to end.

### Claude's Discretion

- Whether the fix lands as one plan or splits server/client across two.
- The exact Hebrew wording for the status row and step label, within the constraint that it must not claim signing or chain anchoring.
- Error-surface shape for a failed write, provided it is Hebrew/RTL and never leaves the user believing an unrecorded vote counted.
- Whether to keep, narrow, or delete the now-unused `gpsCoordinates` and `paymentTxId` handling rather than leaving dead branches.
- Test strategy and placement, consistent with the existing suite under `apps/web/src/__tests__/`.
</decisions>

<specifics>
## Specific Ideas

- The route's own docstring at `ParticipationFlow.tsx:76` already names the cause: server recording "hooks in once the participate API drops its payment-shaped contract." That is exactly this phase — drop the contract, then hook it in.
- `hasUserParticipated` → `getUserVote` means the already-voted path can return the *existing* ballot rather than a bare 400. That turns a double-submit into an idempotent success and lets the client show the real receipt for the vote already cast.
- The vote page has a `hasVoted` state (`page.tsx:468`) currently set from client state only. Once the server is authoritative, that flag should reflect a server-known fact.
- `incrementVoteOption` already falls back to a read-modify-write when the `increment_vote_option` RPC is missing (`db.ts:993-1005`) — that fallback is not atomic and is worth noting if concurrency matters at launch volume.
</specifics>
