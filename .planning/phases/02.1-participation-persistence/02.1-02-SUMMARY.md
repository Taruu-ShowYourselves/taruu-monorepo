# Phase 02.1 Plan 02: Participation Primitives Summary

**`recordUserVoteOnce` (idempotent ballot insert on SQLSTATE 23505) and `checkVoterEligibility` (server mirror of the client's `isEligibleToVote`), both unit-tested without a live database.**

## Accomplishments
- `recordUserVoteOnce` in `db.ts`: a clean insert returns `{ created: true, vote }`; a `UNIQUE(user_id, vote_id)` violation (23505) reads the existing ballot back and returns `{ created: false, vote }` without throwing; a 23505 with no readable row, or any other error code, still throws.
- `apps/web/src/services/verification/eligibility.ts`: `hasVerifiedResidency` (pure mirror of the client's residency rule), `decideVoterEligibility` (pure, checks `identity_score >= 40` before residency), `checkVoterEligibility` (async shell loading `getActiveVerificationRun` and short-circuiting the DB call when identity already fails).
- 14 passing unit tests across both primitives, plus the pre-existing 60-file / 713-test web suite stays green.

## Decisions Made
- Eligibility reconciles without divergence: the server's pre-existing `identity_score >= 40` gate is kept (every Google sign-in already scores 40, so it blocks nobody the client would admit) and layered on top of an exact mirror of the client's residency rule. Per the CONTEXT.md decision, no relaxation was needed and there is nothing to flag as a stricter-server-check divergence.
- `recordUserVoteOnce` is additive, not a replacement, because the payments webhook (`apps/web/src/app/api/payments/webhook/route.ts:191`) depends on `recordUserVote`'s throwing signature and is out of this plan's file scope.

**Git-index note (process, not code):** This plan ran in parallel with 02.1-01 and 02.1-03 in the same working tree. Between staging (`git add`) and committing Task 3's test file, a concurrent agent's `git add` for its own files (`apps/web/src/app/api/user/participations/route.ts` and `apps/web/src/__tests__/api/user-participations.test.ts`, both listed in 02.1-01's `files_modified`) landed in the shared index and was swept into this plan's Task 3 commit (`d59e15c`) alongside `participation-primitives.test.ts`. This was caught by inspecting `git show <hash> --stat` immediately after committing. A subsequent attempt to correct the commit boundary (`git reset --soft HEAD~1`) itself raced with a second concurrent commit (02.1-03's `7fd9e2d`, which had landed on top in the meantime) and briefly un-committed that plan's work; it was immediately restored with an identical commit (content and message unchanged, new hash `c5d04e6`) via `git reflog`. Given the risk of further collision from rewriting a commit that other agents may already be building on, the two foreign files were left inside `d59e15c` rather than force-split out — their content is correct and belongs to 02.1-01, just mis-attributed to this plan's commit. No content was lost or altered; `git diff --stat` confirms `apps/web/src/lib/verification.ts` is untouched and `recordUserVote`'s signature is unchanged. Flagging here so the 02.1-01 executor/orchestrator is aware its `route.ts` and `user-participations.test.ts` changes are already on the branch (inside `d59e15c`) rather than in a commit of its own.
