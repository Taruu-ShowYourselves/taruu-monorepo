# Phase 02.1 Plan 04: Rewrite `/api/votes/[id]/participate` to the Free Contract Summary

**`POST /api/votes/[id]/participate` now accepts `{ optionId }` alone, persists through the idempotent `recordUserVoteOnce`, and can no longer 402 on a missing payment or 503 on a dead Qubik chain service.**

## Performance

- **Duration:** ~10 min
- **Completed:** 2026-08-02
- **Tasks:** 2/2
- **Files modified:** 2

## Accomplishments
- The route's request contract is now exactly `ParticipateRequestSchema` (`{ optionId }`) via `safeParse` — `paymentTxId` and `gpsCoordinates` are gone from both the schema and the handler, and a missing/invalid `optionId` returns 400 without naming either removed field.
- Server-side eligibility now runs through `checkVoterEligibility` (identity `>= 40` AND residency mirror of the client's `isEligibleToVote`), replacing the raw inline `identity_score < 40` check and the per-vote GPS gate (`verifyCheckIn`) entirely.
- Persistence goes through `recordUserVoteOnce`. `incrementVoteOption` and the `votes.participant_count` bump run only when `created === true` — a duplicate submit returns the existing ballot with `alreadyRecorded: true` and moves nothing.
- The `qubikService.recordVote` call and its hard 503, the 3-token `qubikService.mintTokens` mint, and the `sendPaymentReceiptEmail` call are all removed with no replacement — a dead chain service can no longer reject a resident's vote, and no consideration is issued for a ₪0 vote.
- The response now returns the server row's `id` and `created_at` (never a fresh client-side timestamp), matching `ParticipateResponseSchema` exactly — this is the contract plan 05 will code its client against.
- The route test file's `participate` describe block (17 tests) was rewritten end-to-end for the free contract, including the duplicate-submit and chain-outage regression cases; the `verify-location` and `participated` describes are byte-identical to before.
- Full web suite: 60 files / 714 tests green. Typecheck clean (`tsc --noEmit`, no errors). Lint clean (0 errors; 2 pre-existing unrelated warnings in `postcss.config.mjs` / `worker.ts`).

## Decisions Made
- The plan's own acceptance-criteria greps for the test file (`paymentTxId` count `0`, `402` count `1`) directly contradict the plan's own mandated, verbatim test case 3 assertion (`not.toContain('paymentTxId')`) and case 4's required title (`'accepts a body with no paymentTxId and never returns 402'`). Followed the literal test content the plan specified — it is more precise and unambiguous than the blanket grep — and verified the *route source file* (the actual contract surface downstream consumers depend on) against the same greps, where it is clean (`paymentTxId`: 0, `gpsCoordinates`: 0, `402|503`: 0). This mirrors the pattern both wave-1 executors already documented: this plan's blanket file-wide greps are approximate sanity checks, not a literal spec, when they conflict with an explicit, itemized instruction a few lines above them.
- Padded the `alreadyRecorded` count to the required minimum of 3 by adding a real assertion (chain-outage test also checks `alreadyRecorded: false`) rather than an inert duplicate, since the chain-outage path is exactly the kind of full happy-path response worth checking end-to-end.
