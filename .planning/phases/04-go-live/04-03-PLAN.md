ledger to reconcile with zero open mismatches. Nothing in this repo can do that today — there is no

the human feeds it a settlement export at the checkpoint.

**The internal ledger is `payments`, not `transactions`.** The roadmap's phrase "the internal
`transactions` table" has no referent — no such table exists in any migration. The real table
(`supabase/migrations/20240101000000_initial_schema.sql:148-168`):

```sql
CREATE TABLE payments (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  type payment_type NOT NULL,             -- 'vote_participation' | 'vote_creation'
  amount INTEGER NOT NULL,                -- AGOROT (cents), not shekels
  currency TEXT DEFAULT 'ILS',
  status payment_status DEFAULT 'pending',-- 'pending' | 'completed' | 'failed' | 'refunded'
  provider TEXT DEFAULT 'green_invoice',
  provider_id TEXT,                       -- the GI document id (null until settled)
  idempotency_key TEXT UNIQUE NOT NULL,
  vote_id UUID,
  option_id TEXT,
  metadata JSONB,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

**How the GI document id reaches `provider_id`** — `apps/web/src/app/api/payments/webhook/route.ts:108`:
```ts
const claimed = await markPaymentCompleted(payment.id, event.paymentId);
```
`markPaymentCompleted` (`lib/supabase/db.ts:545-565`) sets `status='completed'` and `provider_id` in
one statement guarded by `.eq('status','pending')`, so only one webhook delivery wins.
`event.paymentId` comes from `parseWebhookEvent` (`services/payments/greenInvoice.ts:328-341`), which
reads `payload.id || payload.documentId || payload.paymentId || ''` — GI's field name varies by
account and flow, hence the OR chain.

**Consequence for matching:** a payment that never received a webhook has `status='pending'` and
`provider_id = null`. It cannot match on document id at all — yet it may have settled at GI. That is
the money-losing case and it must surface as its own bucket, not vanish.

**Second, independent ledger:** `webhook_events` (`event_id`, `provider`, `event_type`,
`payload_hash`, `idempotency_key`, `status`). A GI-only row whose document id DOES appear in
`webhook_events` means notify arrived but fulfilment broke; one appearing in neither means notify
never arrived. The report distinguishes these via an optional third input.
