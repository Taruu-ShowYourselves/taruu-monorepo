# Milestone v1.0 Audit — Taruu: P0 Payments + Go-Live

**Audited:** 2026-08-02
**Status:** `gaps_found`
**Scope:** Phases 1-6 (ROADMAP.md lists six phase sections; the Overview bullet list and `phase_count` still say four — Phases 5 and 6 were appended today in commit `83f5681` from GitHub issue #79)

## Headline

The milestone as written no longer describes the product that shipped. Between the last STATE.md update (2026-06-30) and today, 56 commits landed outside the GSD loop — including `cfa5d25` (2026-07-29) which made participation free, deleting the economic premise that Phase 3 and Phase 4 were built on. Five payment requirements are not merely unbuilt; they are **contradicted by shipped code**.

Separately and more urgently, the audit surfaced a **P0 correctness defect that no requirement covers**: the participation flow never reaches the server. A resident completes a vote, is shown a blockchain-seal receipt, and nothing is persisted.

## P0 Outside the Requirement Set

`apps/web/src/app/[locale]/votes/[id]/flow/ParticipationFlow.tsx:149-157` seals a vote with `mockHash()` — `crypto.getRandomValues` over 32 bytes — plus a fabricated block number, sets local React state, and stops. The file has zero `fetch()` calls. Its own docstring at `:76` says server recording "hooks in once the participate API drops its payment-shaped contract" — which is accurate, and which means the contract mismatch introduced by making participation free was never resolved, only bypassed in the UI.

The user-visible consequence: residents are shown `נחתם` and `✓ חתום בבלוקצ׳יין · בלתי ניתן לשינוי` over a random number, on a live site, for votes that were never recorded. No requirement in this milestone covers it, because the milestone assumed participation would always be payment-gated.
